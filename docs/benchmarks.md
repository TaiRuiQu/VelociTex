> **+20.5%**，空对照 99.87%–100.19%），
> 对 Chrome 里的 KaTeX(JS)（156–189 µs/公式）是 **5.9–7.1 倍**，
> 对 Node 里的 KaTeX(JS)（232–288 µs/公式）是 **8.7–10.8 倍**——
> 差距主要出现在 WebAssembly 与浏览器这一层。下文先给出当前真实数据与差距分析，
> 之后保留 preview6 的历史页面作为回归参考。
>
> **这一轮的三处改动只买到了 WASM 侧的时间**：复用状态不再走 `thread_local` 的
> 初始化守卫，类名表不再清零它从不读的那 108 字节。原生侧配对 A/B 读
> +0.86% ~ +1.54%（空对照 ±0.3%），浏览器侧读 **-4% ~ -5%**
> （core 直测，最快一轮与中位轮同向）。原因见"这一轮的增量"一节：
> 省掉的是 WebAssembly 里的运行时调用，libstdc++ 本来就把它们内联掉了。
>
> **这一轮还修掉了一个真实的缺陷**：SVG 的路径数据原来是一个放在 arena 节点里的
> `std::string`，而节点从不析构，于是字符串的堆缓冲永远不释放——一个页面渲染约
> 三万条公式就会耗尽固定的 WebAssembly 堆。详见"一个泄漏"一节。
>
> **这一轮把渲染器的"短文本比较"从 C 库调用改成了内联比较**：`string_view` 的
> `compare` 比较的是两个长度中较短的那个，这个长度只有运行期才知道，于是
> `memcmp` 无法被内联——每一次比较都是一次对 C 库的调用，而渲染器对每个原子
> 都要问好几次（节点的类决定相邻原子的间距，MathML 节点的标签决定它怎么写）。
> 现在字面量按**编译期已知长度**来比（`same_text(a, "mord")`），是一次加载加一次
> 比较。Node 配对 A/B 读 **+1.31% / +1.48%**（两序同向），浏览器 core 直测的
> 中位轮 **9.800 ms → 9.450 ms（-3.6%）**、最快轮 8.700 ms → 8.650 ms，
> 原生配对 A/B 读 +1.37% / -0.93%（空对照 +0.10%）——原生侧中性是应该的：
> 省掉的那次调用在原生构建里本来就很便宜。**把同样的改动用在 UTF-16 那一侧
> （解析器的命令名、符号表与宏表的哈希）是负结果**，详见"这一轮的增量"一节。
>
> **这一轮把解析器的任务从"每次转换拷三次"降到"拷一次"**：任务是一个没有
> move 构造的普通结构，所以"移动"也是拷贝——注释里写"临时量是被移动而非拷贝
> 进去的"是错的。拷贝任务的那一行是解析器里最热的一行（`parser.cpp:1607`，
> `ParserState::Run` 的 130 个样本里占 12 个）。现在任务只被拷进任务栈一次，
> 编辑就地作用在栈里那一份上。Node 配对 A/B 读 **+1.30% / +1.90%**（两序同向），
> 浏览器**同一页面里两个模块的配对 A/B** 读快 **1.1%–2.3%**（两序各两次，
> 空对照 0.00%），模块还小了 **2,610 字节**——拷贝就是指令。

## 当前实现（C++ Core → WASM，KaTeX 逐字节一致）

测试环境：Linux x64，2 核 / 3 GB RAM，gcc 11.4（Release），Emscripten 3.1.74
（`-O3 -flto -std=c++20 -fwasm-exceptions -fno-rtti --no-entry -sENVIRONMENT=web
-sALLOW_MEMORY_GROWTH=1`），Node 24 与 Chromium（headless）。语料为
`benchmarks/workloads.json` 的 36 条冻结公式。

> **口径说明**：下面所有数字都用与浏览器基准相同的口径测量——整条语料预热 25 轮，
> 再测 25 轮取最快一轮；原生侧用 `CLOCK_PROCESS_CPUTIME_ID`（进程 CPU 时间）复核，
> 避免这台 2 核机器上其它进程造成的争用污染。KaTeX 与 VelociTex 的阶段数字来自
> 两个脚本，因此**倍数要看区间而不是单点**。这台机器的负载会让 KaTeX(JS) 的
> 读数波动，Node 下在 232–288 µs/公式之间、Chromium 下在 156–244 µs/公式之间
> （门禁脚本这两轮的读数是 153–156 µs 的最快轮与 186–214 µs 的中位轮）；
> 下面取的是同一会话里最好的一轮。
>
> **表里的 WASM 数字是 2026-10-23 那次测量的结果**，后来又做了两处改动
> （见"这一轮的增量"一节：MathML 的值池与符号文本、HTML 构建器里每符号的临时
> 字符串）。同一个时间窗内的前后对比是：MathML 阶段 13.49 → 12.09 µs，
> 整条流水线 **-2.4%**——它们省掉的是 libc++ 的跨模块调用，而不是算法。
>
> **同一份 KaTeX 在两个运行时里差 40%**：Node 24 的 KaTeX(JS) 比 Chromium 里的
> 同一个 `katex.mjs` 慢约 40%。引用倍数时必须写清楚对手跑在哪个运行时里，
> 否则同一个数字可以被读成 2.5 倍也可以被读成 5.6 倍。

### 两端引擎的阶段分解（同一台机器，同一语料）

KaTeX(JS) 与 VelociTex 的 HTML / MathML 输出结构完全对应，因此可以逐阶段比较：

| 阶段               |  KaTeX (JS) | 原生 (gcc 11.4) | 原生 (clang 20) |      倍数 | VelociTex C++ WASM (Node) |
| ------------------ | ----------: | --------------: | --------------: | --------: | ------------------------: |
| 解析               |      ~29 µs |         ~6.3 µs |         ~5.2 µs |      5.6× |                   ~5.7 µs |
| HTML 构建+序列化   |     ~145 µs |        ~18.3 µs |        ~16.3 µs |      8.9× |                  ~26.3 µs |
| MathML 构建+序列化 |      ~24 µs |         ~5.9 µs |         ~5.9 µs |      4.1× |                  ~10.1 µs |
| **合计**           | **~215 µs** |    **~32.2 µs** |    **~29.3 µs** | **~7.3×** |              **~42.1 µs** |

原生侧 32.2 µs 的内部构成（`/tmp/stages` 口径，进程 CPU 时间，最快一轮）：
解析 6.3 µs、**HTML 树构建 13 µs + HTML 序列化 6 µs**、MathML 6.5 µs。
解析阶段内部再分：宏展开（分词 + 展开）1.9 µs，语义树构建 4.2 µs。

**这张表是本项目最重要的结论**：C++ Core 在原生构建下**比 KaTeX(JS) 快约 5–7 倍**，
逐字节一致并没有牺牲速度。剩下的差距不在算法，而在 **WebAssembly 与浏览器这一层**。

#### 这张表是怎么量出来的，以及它的边界（2026-10-24 复核）

`vt_render` 的三个输出模式（0 = HTML+MathML、1 = 只有 HTML、2 = 只有 MathML）
都包含解析，所以 `parse = mode1 + mode2 - mode0`。**这个口径有一处系统误差**：
模式 0 的 payload 是模式 1 的两倍（HTML 里嵌着 MathML），多出来的那份拷贝与
追加让模式 0 比"P + H + M"更贵，于是相减出来的"解析"被低估了。

**更可靠的口径是消融法**：把某一阶段整个关掉（用编译期开关），量同一模式下
两个构建的差。两个构建在同一进程里交替测量（每轮轮转顺序，避免"总是第一个
测"带来的偏差），取逐轮比值的中位数。用这个口径在当前源码上量到的是：

| 量                           |      读数 | 占整条 WASM 流水线 |
| ---------------------------- | --------: | -----------------: |
| 整条流水线（模式 0）         |  47–49 µs |               100% |
| HTML 阶段                    | ~30–32 µs |           **~65%** |
| MathML 阶段                  | ~15–17 µs |           **~35%** |
| 解析                         |   ~5–6 µs |               ~12% |
| 模式 0 相对"P+H+M"的额外开销 |     ~4 µs |                ~8% |

**MathML 阶段内部**（同一套消融法）：

| 量                                              |        读数 | 占 MathML 阶段 |
| ----------------------------------------------- | ----------: | -------------: |
| 遍历语义树（样式、尺寸、颜色）                  |     ~1.4 µs |            ~8% |
| **建图**（`Writer::build`，每公式 32.9 个节点） | **~5.2 µs** |       **~31%** |
| **序列化**（`Writer::serialize`，每公式 64 步） | **~3.0 µs** |       **~18%** |
| 其余（准备与外壳）                              |       ~2 µs |           ~12% |

**这一节订正了旧文档里的两个数字**：旧文档写的是"遍历 15% / 建图 50% /
序列化 35%"，那是**原生**口径下的估计；WASM 上建图与序列化加起来是
**~8.2 µs = 整条流水线的 17%**，而遍历只有 1.4 µs。**"边建边写"能省下的
上界就是这 8.2 µs**（原生口径下旧文档估的 60% 偏乐观，WASM 口径下是 ~50%）。

**建图与序列化是同一个"两次遍历"的两半**：`build` 先把语义树翻译成一张
MathML 节点图（记属性表与值池），`serialize` 再遍历这张图写 markup。
把两者合成一次遍历，就是路线图上的"边建边写"。

> **WASM 阶段的拆分方法**：`vt_render` 的三个输出模式（0 = HTML+MathML、
> 1 = 只有 HTML、2 = 只有 MathML）都包含解析，所以
> `parse = mode1 + mode2 - mode0`。测量用 `process.cpuUsage()`（进程 CPU 时间）
> 而不是墙钟——这台 2 核机器负载常年 2.2+，墙钟的波动比要测的差异还大。
> 另有两点必须注意：两个构建要**在同一进程里交替**比较；
> **输入缓冲必须够大**，否则会写穿 WASM 堆、把公式搞失败——失败的公式更快，
> 于是看起来像"优化生效"了（本轮就踩过一次，把 45 µs 误测成 37 µs）。
> **每轮里构建的顺序要轮转**：固定顺序会让"总是第一个测"的构建系统性地慢，
> 实测能把 5 µs 的差异读成 3 µs 的差异，方向甚至是反的。

- 原生 32.2 µs（gcc）/ 29.3 µs（clang）→ WASM（Node）42.1 µs：WASM 运行时与线性内存的固定开销（约 1.44×）。
- WASM（Node）42.1 µs → 浏览器 44–52 µs（纯 WASM 调用）/ 50–62 µs（完整 npm 路径）：
  浏览器内多出的约 6–7 µs 是 **JavaScript 那一层**（编码源文件 1.2–1.4 µs、
  每公式一次 `TextDecoder.decode` 0.42 µs、选项 JSON 0.46 µs、promise 与结果对象）。
  逐段数据见"浏览器路径里胶水到底值多少"一节。

**当前会失败**——这是有意保留的未达成项，而不是被弱化的测试。

#### 浏览器基准的估计量：为什么改成"逐轮配对比值的中位数"

基准脚本以前对每个引擎各取"最快的一轮"再相除。在负载 2.3–2.9 的 2 核机器上，
这个估计量不可靠：两个引擎的最快一轮很可能落在**不同的负载窗口**里，
同一对构建两次跑出来的结论能差 6%。现在脚本改成：

- 预热 25 轮（两个引擎同样待遇），然后测 **120 轮**，每一轮先测 KaTeX、
  紧接着测 VelociTex；
- **报告逐轮比值的中位数**，同时报告两个引擎的最快轮与中位轮、以及"最快一轮
  的比值"作为对照；
- 顺带把**逐字节一致性也变成断言**（原来只打印不一致的公式）。

同一台机器上两种估计量给出的读数一致（3.17× 与 3.26×），说明这个改动不是为了让
数字好看，而是让数字在负载波动下稳定。

**预热不是瓶颈**：浏览器里的 WASM 确实要很多轮才进入稳态（第一轮比稳态慢
10–20 倍），但 KaTeX 的 JIT 同时也在预热。把预热从 25 轮延长到 120 轮，
稳态倍数没有变化（实测各轮次窗口的中位比值：0–24 轮 2.79×、25–99 轮 2.60×、
100–199 轮 2.59×、200–299 轮 2.81×、300–399 轮 2.77×）。

#### 浏览器路径里胶水到底值多少（逐段拆解）

在浏览器里逐段量了 npm 完整路径（同一个页面、**同一个** WASM 实例）。每一对都是
A,B,B,A 的配对顺序，取逐轮比值的中位数；**语料在计时轮内重复 6 次**，否则
`performance.now()` 的 100 µs 分辨率会把每公式 2.8 µs 的差异整个吞掉。

| 段                                         | µs/公式 | 说明                                                |
| ------------------------------------------ | ------: | --------------------------------------------------- |
| `katex.renderToString`                     | 182–244 | KaTeX 侧（这台机器负载高时读数会漂）                |
| `velocitex.renderToString`（npm 完整路径） |   50–62 | 公开 API：选项 JSON + promise + 结果对象            |
| `renderKatexMath`（npm 内部那一层）        |   48–57 | 核心 + 编码 + 解码                                  |
| 核心（`vt_render`，只调 WASM）             |   44–52 | 减去编码与解码                                      |
| `TextDecoder.decode`（1162 字节）          |    0.42 |                                                     |
| 编码源文件                                 | 1.2–1.4 | 包自己编码，写进已缓存的视图                        |
| 选项 JSON                                  |    0.46 | `compileOptions` 自己拼 JSON，不走 `JSON.stringify` |
| 把 payload 复制出来再解码                  |    10.2 | 复制比解码本身还贵                                  |

**配对比值**（这是可信的部分，绝对值会漂 ±20%）：

| 配对                                      |      比值 | 读法                                              |
| ----------------------------------------- | --------: | ------------------------------------------------- |
| 公开 API ÷ 包内快路径                     |     1.061 | 包自己那层（选项 JSON + promise + 结果对象）约 6% |
| 包内快路径 ÷ 裸 `vt_render`               |     1.080 | 编码 + 解码约 8%                                  |
| **公开 API ÷ 裸 `vt_render`**             | **1.146** | **整个 JS 层约 14.6%，内核约 87%**                |
| 裸 `vt_render` ÷ 裸 `vt_render`（空对照） |     1.016 | 这套协议的噪声底                                  |
| KaTeX ÷ 公开 API                          |      3.48 | 与门禁脚本的 3.11–3.35× 同量级                    |

结论：**核心占整条路径的 ~87%，JS 这一层约 6–7 µs（12–15%）**。
胶水里最大的一项已经不是解码（0.42 µs），而是**包的公开 API 那一层**
（选项 JSON、promise、结果对象）。但这一层的天花板也就是 6 µs，
**即使它归零，也只从 3.2× 走到约 3.5×**——内核才是杠杆。

**解码能不能更快**：`TextDecoder.decode` 解 1162 字节要 0.42 µs，
而 `String.fromCharCode.apply` 只要 1.54 µs（看起来慢 3.7 倍）。但 36 条语料里
只有 **7 条是纯 ASCII**，其余含 `∑`、`−` 这类多字节字符，Latin-1 的快路径
用不上；即便只对纯 ASCII 的那部分走快路径，平均也只省 0.4 µs（0.6%）。
不值得为此在胶水里加一条分支。

**选项 JSON 不是杠杆**：核心按 JSON 字符串缓存解析结果，只有字符串变了才重解析。
浏览器基准里 `displayMode` 在两条公式之间来回切换，缓存交替失效——实测这条
路径只值 **0.17 µs/公式**（同一进程交替测量的配对比值）。

**公开 API 的异步包装已经摘掉（2026-10-24，浏览器实测 -1.9%）**：
`renderToString` 原来是 `markup(await compile(...))`——每次调用建一个 promise、
再等一个微任务轮次，调用方拿到结果要等**三个**微任务。现在 `compile` 拆成
**同步快路径**（`compileFast`：模块已加载时直接进核心，返回结果对象）与
**异步慢路径**（`compileSlow`：等模块加载、走 .NET 回退），`renderToString`
先试快路径，命中就**全程不 await**。包的类型契约不变（仍然返回
`Promise<string>`），慢路径的语义逐字未动。

浏览器同页配对 A/B（两个胶水共用**同一个** WASM 实例，36 条语料在计时轮内
重复 6 次，A,B,B,A 顺序，取逐轮比值的中位数）：

| 配对                 |          比值 | 读法               |
| -------------------- | ------------: | ------------------ |
| 新胶水 ÷ 旧胶水（1） |        1.0194 | 新版本快 **1.94%** |
| 新胶水 ÷ 旧胶水（2） |        1.0180 | 1.80%              |
| 新胶水 ÷ 旧胶水（3） |        1.0198 | 1.98%              |
| 空对照（新 ÷ 新）    | 0.9973–0.9999 | 噪声底 ±0.3%       |

语义逐项对照（在 Node 里把 WebAssembly 从磁盘喂给加载器，对 31 个用例比较
返回值与抛出的错误）：**快路径的用例全部逐字相同**；只有 5 个走 .NET 回退的
用例不同，差别**仅在错误信息里的目录路径**（两个副本装在不同目录）。

**一个测量陷阱**：一开始把「npm 包的 WASM 实例」和「手工再实例化一份同样的
模块」放在同一个页面里测，读数显示核心和 npm 包都是 75 µs。实际上两个实例各占
16 MB 线性内存、互相争抢缓存与 CPU，把读数抬高了 50%。**只保留一个实例**，
单实例下测到的是核心 44–52 µs、npm 完整路径 50–62 µs。
教训：测胶水时不要在同一页面里加载第二份模块。

**第二个测量陷阱**：逐段拆解的脚本里，循环变量存的是 `encodeInto` 的**写入长度**
而不是内容偏移，于是缓冲区里始终是最后一个公式，"轮换 36 条公式"那一轮实际渲染
的是长度与内容不匹配的垃圾源，触发 WASM 异常展开后读数 144 µs——
比反复渲染同一条公式（18.5 µs）还慢，于是得出"核心比想象中快"的错误结论。
教训：拆解脚本里凡是写进缓冲区的内容，循环变量必须指向**内容**。

**第三个测量陷阱（最贵的一个）**：`performance.now()` 在 Chromium 里只有
**100 µs** 的分辨率。一轮 36 条公式的核心只要 ~1.7 ms，也就是**每公式 2.8 µs
的量化步长**——对我们 6%，对 KaTeX 0.3%。凡是小于 3 µs/公式的差异，
**必须在计时轮内重复语料**（现在用 6 次，轮长 ~11 ms，步长 0.46 µs）。
本项目里被这个陷阱读错的三条结论：胶水 9 µs（真值 6–7 µs）、
npm 包自己那层 3.7 µs（真值约 6%）、解码 4.6 µs（真值 0.42 µs）。
教训：**先算一遍分辨率，再看数字**。

**第四个测量陷阱**：把 KaTeX 和 VelociTex 的段放在同一轮里测，KaTeX 那一段的
分配量会把垃圾回收推到紧随其后的段上，读数出现"公开 API 比它内部的快路径还快"
这种不可能的结果。分段测量时 **KaTeX 单独一组**，VelociTex 的各段在另一组里。

### 两个构建怎么比才可信（2026-10-23 的方法学修正）

在负载 2.3–2.9 的 2 核机器上，**"各取最快样本"这个估计量是不可靠的**：同一对构建
两次跑出来的结论能差 6%（-5.96% 与 -6.85%，而后一次换成配对估计量只有 -1.8%）。
单轮比值的散布高达 ±40%，所以"最快样本"只是采到了负载最低的那一刻，两组样本
落在不同的负载上。

**可靠的估计量是逐轮配对比值的中位数**：每一轮里先测 A、紧接着测 B（两者在同一个
进程里），用这一轮的比值做样本，至少跑 1000 轮，取中位数。它的噪声底是 **±0.6%**
（用同一个构建对自己测出来的），所以 **1% 以内的差异不算结果**。
这个估计量与原生侧的测量对得上：同一处改动，原生单阶段能看到 3.2%，配对中位数
在 WASM 侧也是 1.9%。

**每个新结论都要先跑一次空对照**（同一个构建对自己），确认读数在噪声底以内。

#### 内核改动在这台机器上分辨不了 1%：换两个更硬的量（2026-10-24）

上面那个配对估计量对 **JS 胶水** 够用（噪声底 ±0.3%），但对 **内核** 不够：
2026-10-24 用它对比两个内核构建时，逐轮比值的分布是 p25=92.9%、p75=109.0%——
**四分之一的轮次散在 ±8% 里**，同一对构建重复四轮得到的估计量在 99.0% 与 103.4%
之间跳。原因是机器的干扰（这台机器的 load 在 1.7–2.0）持续的时间远长于一次
测量窗口，于是它只打到两个构建中的一个。空对照在同一协议下读 99.3%–100.4%
（噪声底约 ±0.5%），所以 **内核的 1% 改动在这台机器上无法用墙钟分辨**。

这一轮换了两个更硬的量：

1. **每组的最小值**（`/tmp/wasmmin.mjs`）：把 36 条语料切成 6 组，两个构建在每组内
   交替测量 6 次，**只保留每组的最小值**——最小值就是"机器没有插队"的那一次；
   两个构建的最小值之和的比值就是结果。空对照读 99.5%–100.0%（很稳），
   同一对构建的两种顺序给出的读数分别是 102.3%–104.0% 与 97.96%–99.55%
   （**两个顺序都指向同一个方向**）。
2. **分配计数**（确定量）：核心里本来就有池分配器的计数器
   （`native/core/pool_alloc.cpp` 的 `alloc_count_get()`），把它导出成一个测量构建，
   数同样几条公式要多少次堆分配。这个数是**确定的**，不受机器负载影响。

### 原生侧的配对 A/B：噪声底 0.5%，能分辨 1% 的内核改动（2026-10-24）

上面两个量都在 WASM/Node 侧，而 Node 侧的墙钟在这台机器上分辨不了内核的 1%。
**原生侧可以**：同一份源码用同一个编译器（emsdk 的 clang 20）编成两个驱动，
两个驱动交替跑同一组语料，计时用 `CLOCK_PROCESS_CPUTIME_ID`（进程 CPU 时间，
不受其它进程的争用影响），每组取最小值。

- **空对照**（同一个二进制对自己）：**100.02%**（逐轮配对比值的中位数 100.01%），
  比 WASM 侧的空对照（±0.3%）还好一点。
- 所以原生侧的 A/B **能分辨 1% 的内核改动**，这一轮的每一步都是用它判的。

驱动在测量之前会先把整条语料渲染一遍（热身），所以"符号表一次性建表"的成本
不在测量窗口里；工作区与文档都复用（和 WASM 入口一样），因此原生侧与浏览器侧
测的是同一件事。

### 阶段的消融（2026-10-24，四个构建在同一个进程里交替）

用编译期开关把每个阶段关掉（`-DVELOCITEX_ABLATE_MATHML`、
`-DVELOCITEX_ABLATE_HTML_SERIALIZE`、`-DVELOCITEX_ABLATE_HTML`），
四个构建放进同一个进程交替测量，得到这条流水线在 **WASM** 上的实际构成：

| 阶段                 | 占比（WASM） | 原生侧同口径 |
| -------------------- | -----------: | -----------: |
| 解析                 |      ~17–20% |         ~20% |
| HTML 树构建          |      ~40–44% |         ~40% |
| HTML 序列化          |      ~16–21% |         ~16% |
| MathML 构建 + 序列化 |      ~17–24% |         ~24% |

这修正了上面那张表里的一个印象：HTML 阶段并不是"序列化占大头"，**树构建才是
HTML 阶段里更大的那一半**（DOM 树的分配、类名表、样式表、尺寸计算都在里面）。

**WASM 税的准确数字**：原生 29.5–30.0 µs/公式，同样的语料在 Node 的 WASM 里是
**58 µs/公式**，即 **≈1.85 倍**；浏览器里 `wasm.vt_render` 是 44–52 µs/公式，
即 **1.5–1.8 倍**。按阶段拆开（WASM ÷ 原生）：解析 1.65×、HTML 树构建 2.19×、
**HTML 序列化 2.55×**、MathML 1.44×——**税集中在把布局变成标记文本的那一段**，
因为那一段全是内存访问，而 WASM 的内存访问比原生贵（**但贵的不是边界检查**，
见下面「WASM 税不是边界检查」一节）。
这也解释了为什么原生侧（指针可以直接算地址）和 WASM 侧的差距，比"同样的指令
多跑 30%"要大。

### 第二轮增量：类名表重写 + 一个泄漏（原生侧配对 A/B）

这一轮改了三件事：内核的类名表、一个**发布包里已经存在的泄漏**，以及一处由前两
者带来的拷贝。

| 改动                                                           | 原生侧配对 A/B                        | 备注                                                                    |
| -------------------------------------------------------------- | ------------------------------------- | ----------------------------------------------------------------------- |
| **类名表重写**（`domtree.hpp`）                                | **+5.8% ~ +6.5%**（相对重写前）       | 掩码与 `ClassFlagOf` 全部删除，类名改成内联的名字数组，查找变成逐名比较 |
| **修 SVG 路径数据的泄漏**（`HtmlPath` 改用 `ArenaText`）       | 合并测量                              | 泄漏修复本身要付出约 2%：路径数据现在要拷进 arena                       |
| **类名表按右值引用传递**（`MakeSpan`/`MakeSymbol`/`HtmlSpan`） | 中性                                  | 每节点少两次 64 字节的拷贝；WebAssembly 里这两次拷贝是两次 libc++ 调用  |
| **合计**（相对上一版已发布的构建）                             | **+5.0%**（逐组中位 95.29% / 95.42%） | 两种顺序同向；空对照 99.87%                                             |

原生侧 28.0 µs/公式 → **约 26.6 µs/公式**（同一台机器、同一个编译器、同一份语料）。

**类名表为什么值得重写。** 旧实现把类名拼成一段文本放进 arena，再用一个 16 位掩码
记住这个节点带了哪些"已知类"。新实现直接内联一组名字指针（`const char* names_[12]`
加长度），节点不再为类名分配任何内存，掩码与 `ClassFlagOf` 一起消失，`Has`/
`IndexOf` 变成逐名比较。尺寸类名、脚本回退类名、分隔符的尺寸类名都变成静态表项。

**这个重写一开始把逐字节门禁打到了 5248/5411。** 类名变成视图之后，五个调用点
把**临时字符串**交给了类名——`"col-align-" + align`、分隔符的 `"size" + to_string`、
`accent.cpp` 里的局部 `vector<string>`、`arrow_prefix + "-arrow-pad"`、还有框的标签。
临时字符串一死，类名就指向了被复用的内存，写出去的是 `class=")   align-c"` 这种
垃圾。修法有两条：一是把这些名字换成静态表项（`col-align-l/c/r`、`size1..size4`、
`hide-tail`/`halfarrow-*`/`brace-*`、`x-arrow-pad`/`cd-arrow-pad`、`fbox`/`colorbox`/
`fcolorbox`/`angl`），二是加一个**检测器**：`-DVELOCITEX_CHECK_CLASS_NAMES` 会记住
每个类名的字节，写出时再比一遍，一旦发现被改动就报出来。全语料（5,411 条）跑下来
**零悬垂**。语料里最宽的类名表是 **8** 个名字，容量 12 够用。

顺带修掉的一个真 bug：**尺寸类名的表只到 `size9`，而 KaTeX 的尺寸是 1 到 11**
（`\Huge` 是 11）。越界时名字落进一个 `thread_local` 缓冲，下一次调用就把上一个
名字冲掉了。表补到 11，越界时名字拷进 arena。

### 第三轮增量：少搬一次数据——WebAssembly 里的 libc++ 调用

上一轮的最后一条（"两端引擎对同一处改动的反应相反"）留下了一个明确的线索：
`__memcpy` 的份额从 1.41% 涨到 4.59%，其中 **2.43% 挂在
`HtmlNode::WriteMarkup` 下面**。这一轮照着这条线索做，**不改动算法，只把"长度在
运行期才知道"的拷贝改成"编译器知道长度"的内联拷贝**。

改了三处：

1. **`TagBuffer::Append`**（`native/core/html/markup.hpp`）：开头标签是在栈上的
   缓冲里拼出来的，每一个类名一次 `std::memcpy(data_ + length_, text, length)`——
   长度是运行期的，于是它变成一次 **libc++ 的跨模块调用**。现在换成一个定长步进的
   循环（`detail::CopyBytes`），每次搬 8/4/2/1 字节，全部是编译期常量，编译器把它们
   变成 load/store。
2. **`MarkupBuffer::Append`**：短片段（≤ 48 字节）走原有的首尾重叠拷贝，长片段改成
   同一个 `CopyBytes`，于是它也不再调用 libc++。
3. **分隔符那一族函数**（`delimiter.cpp` / `delimiter.hpp`）的 `ClassList` 参数从
   **按值**改成**右值引用**。`ClassList` 是 64 字节（wasm32 里 12 个 4 字节指针加
   12 个长度），按值穿过函数边界就是一次 64 字节的 `memcpy` 调用。上一轮已经改过
   `MakeSpan`/`MakeSymbol`/`HtmlSpan`，这一轮把 `MakeLargeDelim`/
   `MakeStackedDelim`/`MakeCustomSizedDelim`/`MakeSizedDelim`/
   `MakeLeftRightDelim`/`StyleWrap`/`MakeSmallDelim` 补齐（调用点本来就在
   `std::move`，所以是纯签名改动）。
4. **`MakeVList` 的子节点不再先造局部变量再移进 vector**（`build_common.cpp`）：
   `Child` 有 144 字节（两个 `optional<double>`、一个 `ClassList`、两个指针、
   三个 double），"造一个局部的 `Child` 再 `push_back(std::move(child))`"就是一次
   144 字节的移动——在 WebAssembly 里同样是一次 libc++ 调用。现在改成
   `emplace_back()` 之后**在 vector 里就地填字段**，那次拷贝整个消失。

| 测量                                        | 读数                                                          |
| ------------------------------------------- | ------------------------------------------------------------- |
| 原生配对 A/B（两种顺序）                    | **98.66% / 102.44%**（即 **+1.3% ~ +2.4%**），空对照 100.19%  |
| Node 里的 WASM 配对 A/B（两种顺序）         | **+6.2% / +4.1%**（最静窗口估计量），中位比值 +6.7% / +0.9%   |
| 浏览器 core 直测（语料在计时轮内重复 6 遍） | 最快一轮 **-2.9%**、中位轮 **-5.7%**、均值 **-8.0%**          |
| 原生绝对值（同驱动，取 8 轮里最好的一轮）   | 上一版 **28.5 µs** → 这一版 **26.6 µs**/公式（HTML + MathML） |

第 4 项（`MakeVList` 的就地构造）单独量：原生侧**中性**（两种顺序 99.76% /
100.54%，空对照 99.97%——原生侧 libstdc++ 把那次结构体移动内联了，本来就没有
代价），Node 里的 WASM 配对 A/B 读 **+1.9% / +0.5%**（最静窗口）与 **+4.0% /
+2.1%**（逐轮比值的中位数），浏览器的 core 直测读中位轮 **-4.3%**、均值 **-6.3%**
（最快一轮 -1.0%，这一台机器上"最快一轮"是最不稳的估计量）。**它是一次纯粹
"少做事"的改动**，所以风险只有读数噪声。

三端的读数同向，浏览器的三种估计量也同向，这是这一轮可以发布的原因。
逐字节门禁不变：原生 HTML 与 MathML 各 5,411/5,411，WASM 侧 3,660 条文档加
49/49 的错误文档与 41/41 的源范围，浏览器侧 1,651 条加 13/13 的错误路径。

**这一轮说明了一件事**：**在 WebAssembly 里，"一次 libc++ 调用"比"一次拷贝"贵**。
原生侧同样的代码由 libstdc++ 内联成几条指令，所以原生侧看不到差别；只有到了
WebAssembly 才显形，而浏览器是唯一算数的地方。

5. **开头标签不再经过栈上的缓冲**（`domtree.cpp`）：`HtmlSymbol::WriteBody` 与
   `HtmlSpan::WriteBody` 原来先把开头标签拼进一个 256 字节的栈缓冲（`TagBuffer`），
   再把它整段拷进输出缓冲——**标签的每一个字节都被搬了两次**。现在标签直接写进
   输出缓冲，那次整段拷贝消失，`TagBuffer` 整个删掉。

   这一条是这一轮里最大的一条，而且**它的收益在"中位轮"上，不在"最快一轮"上**：
   浏览器的 core 直测四对，最快一轮只快 0.5%，中位轮快 **7.2%**、均值快 **12.1%**。
   原生侧配对 A/B 读 **+3.1% / +3.5%**（两种顺序，空对照 100.13%）。也就是说，它
   砍掉的是**尾部延迟**而不是平均成本——在负载重的机器上，这一项把最差的那几轮
   拉回来了。

   值得记下来的是：这一条**推翻了一个更早的结论**。第一批里"span 的开头标签合并
   成一次写"和 `MarkupBuffer` 一起量过，合计 **+1.25%**；当时"合并写"的收益来自
   `std::string::append` 每次片段都要调用一次 `memmove`。换成自有的 `MarkupBuffer`
   之后，`Append` 已经是"检查容量 + 一次拷贝"，**合并写省下的只是几次容量检查，
   却多搬了一遍整个标签**——所以现在它反而是负收益。

6. **markup 的碎片合并**（`markup.hpp`、`jsnum.hpp`、`domtree.{hpp,cpp}`）：这一轮先用
   一个插桩量了碎片本身——**每条公式（HTML + MathML）784 次缓冲写入，4,407 字节**，
   其中 **92% 的碎片不超过 8 字节，约一半只有 1 到 4 字节**。也就是说，瓶颈不是拷贝
   的字节数，而是**调用次数**：每一次写入都要做一次容量检查、一次长度判断和一次
   拷贝。

   于是把能合并的都合并了：

   - **类名**：空格和名字一起写（`AppendWrapped`），每个类名从两次写入变成一次；
   - **样式声明**：冒号跟键一起写、分号跟值一起写（`MakeEmInto` 多带一个后缀），
     每条声明从四次写入变成两次；
   - **`makeEm` 的结果**：先在栈上的小缓冲里拼好（符号、整数位、小数位、"em"），
     再**一次**写进输出，而不是分四次写；
   - **开头标签**：`<span` 与 ` class="` 合成一次，`"` 与 ` style="` 合成一次。

   结果：**784 次写入降到 625 次（-20%）**，其中 1 到 4 字节的碎片从 317 次降到
   192 次。原生配对 A/B 读 **+1.6% / +1.2%**（两种顺序，空对照 100.01%），
   Node 里的 WASM 配对 A/B 读 **+0.7% / +1.1%**（最静窗口），浏览器的 core 直测
   五对读最快一轮 **-1.0%**、中位轮 **-0.9%**、均值 **-9.3%**。

   这一条也说明了一件关于这条流水线的事：**markup 的写入次数是渲染器的一个乘数**。
   KaTeX 的类名与样式都是短文本，我们把它们拆成碎片写，每条公式就多出几百次
   调用；合并它们不需要动算法，只需要知道碎片有多碎。

7. **MathML 的长度不再需要自己的字符串**（`native/core/mathml.cpp`）：`number()` 原来
   每次都造三四个 `std::string`（一个 `raw`、一个逐字符拼出来的 `digits`、一个
   `s`，外加 `substr` 的临时），`em()` 再拼一次；这些字符串先进值池、再被拷进
   值池。现在数字直接格式化进值池：栈上一个 224 字节的缓冲，格式化完就拷进
   池子，**一个堆分配也没有**。

   这是一条**改写而不是搬运**的改动，收益有两个：一是那几个字符串不见了（堆分配
   现在是**每公式 2.94 次**，HTML 与 MathML 加在一起），二是那几个 `substr` 与
   逐字符的拼接不见了。原生配对 A/B 读 **+0.8% / +1.1%**（两种顺序，空对照
   100.05%），Node 里的 WASM 配对 A/B 读 **+3.3% / +1.1%**（最静窗口），浏览器
   的 core 直测十一对读最快一轮 **-2.0%**、中位轮 **-1.8%**、均值 **-0.7%**。
   逐字节不变：MathML 的 5,411 条全部一致。

**profile 的对照**（同一份源码的 V8 采样剖析，改动前 → 改动后）：

| 函数                    |  改前 |  改后 |        差 |
| ----------------------- | ----: | ----: | --------: |
| `__memcpy`              | 4.59% | 2.25% | **-2.34** |
| `HtmlNode::WriteMarkup` | 8.61% | 6.92% | **-1.69** |

`__memcpy` 少掉的那 2.34 个百分点里，`HtmlNode::WriteMarkup` 名下的是 2.43 个
百分点——**与 profile 里"变长的拷贝"的分布完全对上**。

### 第四轮增量：短文本的比较不再是对 C 库的调用（2026-10-24）

这一轮从**可信的 profile** 出发（方法见"当前源码的 WASM 侧 profile"一节），
找到的不是"多搬了数据"，而是"多问了几次 C 库"。

`std::basic_string_view::compare` 比较的是两个长度中**较短**的那个：

```cpp
traits::compare(_M_str, __str._M_str, min(_M_len, __str._M_len))
```

这个长度只有运行期才知道，于是 `memcmp` **无法被内联**——每一次
`view == "字面量"` 都是一次对 C 库的调用。而渲染器对每个原子都要问好几次：
`SpacingBetween`（相邻原子的间距表）、`cancel_bin`（二元算子的抵消）、
`IsMathClass` 都在比较节点的**类**，MathML 的写入器在比较节点的**标签**。
WASM 的 profile 里 `memcmp` 占 1.11%，其中 `write_attributes` 名下 15.7 ms、
`Writer::build` 名下 9.9 ms、两个 `BuildExpression` 的 lambda 名下 15.9 ms。

改动只有一条规则：**字面量按编译期已知的长度来比**。

```cpp
// native/core/types.hpp
template <size_t N>
inline bool same_text(std::string_view a, const char (&b)[N]) {
    return a.size() == N - 1 && __builtin_memcmp(a.data(), b, N - 1) == 0;
}
```

字面量取**数组**而不是视图，这一点是关键：`_u16` 后缀建出来的是视图，视图把
字面量的长度藏了起来，而视图对视图的比较长度是运行期的。**渲染器这一侧
（HTML 的类名、MathML 的标签）因此改用 `same_text`**；解析器那一侧的命令名
仍是 `_u16` 后缀的比较，**没有动**。

| 测量                             | 读数                                      |
| -------------------------------- | ----------------------------------------- |
| Node 配对 A/B（第一序 / 第二序） | **+1.31% / +1.48%**（两序同向，都更快）   |
| 浏览器 core 直测的中位轮         | **9.800 ms → 9.450 ms（-3.6%）**          |
| 浏览器 core 直测的最快轮         | 8.700 ms → 8.650 ms                       |
| 原生配对 A/B（第一序 / 第二序）  | +1.37% / -0.93%，空对照 +0.10% → **中性** |

原生侧中性是应该的：省掉的那次调用在原生构建里本来就很便宜（glibc 的
`memcmp` 对几个字节是几条指令），贵的是 WebAssembly 里的一次调用。

**负结果：同样的改动用在 UTF-16 那一侧是倒退。** 把解析器的命令名、符号表与
宏表的哈希也换成 `same_text`，Node 配对 A/B 读 **-0.72% / -1.71%**（两序都更慢）。
两个原因：对五到十五个字符的名字，逐字符的循环比一次调用慢；而把几十个字面量
都内联进 `DelimiterFromText` 这样的链式比较，会让模块变大、指令变多——而 WASM
的税恰恰是**引擎生成的指令条数**。这一部分**回退**，只保留渲染器那一侧。

**profile 的坑（值得单独记一笔）**：发布的那处改动，**第一版构建慢了 1.5% 与
4.5%**，而源码只差在 profile 上——核心的 profile 是**构建输入**，被改动的函数
已经对不上它了，编译器只好退回默认的内联与布局启发式。**测量一项核心改动，
先要一份从改动后的源码采来的 profile**：

```bash
CLANG=/usr/bin/clang++-13 LLVM_PROFDATA=/usr/bin/llvm-profdata-13 \
  node tools/reference/generate-pgo-profile.mjs
```

换成新采的 profile，同一份源码读 +1.31% / +1.48%。**这一条对以后每一次核心
改动都成立**，而它此前只写在"profile 必须在已发布源码上采集"这一句里，没有
说清楚"测量之前也要重新采"。

**这一轮发布的产物**：`artifacts/wasm/core/velocitex-core.wasm` 与
`npm/velocitex/dist/runtime/velocitex-core.wasm`，md5 `c1554fae64078387ae52f2bdcfc1a19c`，

### 第五轮增量：解析器的任务每次转换只拷贝一次（2026-10-24）

这一轮的线索来自**可信的原生行级画像**：`ParserState::Run` 的 130 个样本里，
**12 个落在同一行**——`parser.cpp:1607`：

```cpp
auto task = w.Tasks.back();   // 整份 ParseTask 被拷贝一次
w.Tasks.pop_back();
```

解析器是一个任务栈，每次栈的转换都要改任务。改的方式是
`Push(w, changed(task, lambda))`，而这条链上**拷了三份**：

| 位置                                 | 拷贝次数           |
| ------------------------------------ | ------------------ |
| `changed(T value, F edit)` 的参数    | 1（`task` 是左值） |
| `changed` 的返回值                   | 0（NRVO）          |
| `Push(ParserWorkspace&, ParseTask)`  | 1（按值收参）      |
| `w.Tasks.push_back(std::move(task))` | 1（进栈）          |

**关键是：`ParseTask` 是一个没有 move 构造的普通结构（全是标量加一个
`u16string_view`），所以"移动"也是拷贝。** 原来那句注释——"临时量是被移动而非
拷贝进去的"——是错的。

改法只有一条：**任务只被拷进栈一次，编辑就地作用在栈里那一份上**。

```cpp
// native/core/parser.cpp
template <class F>
void PushEdited(ParserWorkspace& w, const ParseTask& task, F edit) {
    w.Tasks.push_back(task);
    edit(w.Tasks.back());
}
```

37 处 `Push(w, changed(...))` 与 10 处 `PushArgument(..., changed(...))` 全部
改成这个形式；`PushHBoxArgument` 的参数从按值改成按引用。

| 测量                                    | 读数                                            |
| --------------------------------------- | ----------------------------------------------- |
| Node 配对 A/B（第一序 / 第二序）        | **+1.30% / +1.90%**（两序同向，都更快）         |
| 浏览器配对 A/B 的最静窗口（两序各两次） | **2.30% / 2.30% / 1.14% / 1.14%**（新的更快）   |
| 浏览器配对 A/B 的逐轮比值中位数         | 2.22% / 2.17% / 0.00% / 0.00%（**被量化偏置**） |
| 空对照（同一个模块测两次）              | 0.00%                                           |
| 原生配对 A/B                            | +1.37% / -0.93%，空对照 -0.48% → **中性**       |
| 产物体积                                | **-2,610 字节**（1,962,364 → 1,959,754）        |

原生侧中性是应该的：省掉的是几次 80 字节的结构拷贝，在原生构建里那点开销淹在
噪声里；**在 WebAssembly 里那几次拷贝是实打实的指令**（税就是引擎生成的指令
条数），所以模块还小了 2.6 KB。

### 第六轮增量：逐字节的循环也是一次对 C 库的调用（2026-10-25）

上一条规则说"长度编译期已知 → 内联；长度运行期才知道 → 一次 libc++ 调用"，
说的是 `memcpy`。但**逐字节拷贝的循环也是同一回事**——LLVM 认得这个模式，
会把它换成一次长度运行期才知道的 `memcpy`：

```cpp
// native/core/html/markup.hpp，detail::CopyShort 的最后一段
for (size_t i = 0; i < length; ++i) {
    target[i] = text[i];     // ← 编译成 call $__memcpy
}
```

`CopyShort` 的这一段处理**一到三个字节**的文本，而标记写入器每条公式要做几百
次这样的拷贝：`em` 值的小数位最后一位、三个字母的类名、MathML 里一个数字的
几位数字。

改法是**两次定长移动**——先拷两个字节，三字节时再补一个字节，没有循环留给
优化器去变成一次调用。

这一轮顺手得到两条方法学结论，都是关于**怎么测**，不是关于内核。

#### 结论一：同一页面里的两个模块，有一个约 1% 的"实例位置"偏置

上一节那个 harness（`/tmp/browser-pair-ab.mjs`，同一页面两个模块）**的偏置
不是零**。之前记的空对照读 1.0000 是因为语料在计时轮里重复 8 遍、一轮 9 ms，
两个最小值落在 `performance.now()` 量化（100 µs）的同一步上。改成重复 6 遍
（一轮 6.6 ms，量化变成 1.5%）之后，**空对照读 -1.15%**：页面里的第二个实例
比第一个快约 1%。

**这一段轮内的顺序抵消不了它**——harness 已经在 A,B,B,A 与 B,A,A,B 之间交替了。
所以原因在**实例**上，不在位置上：两个模块共享引擎的代码空间，被编译到不同
的地址，第二个走运一些。

**能测出差别的 harness 是四个实例的那个**（`/tmp/browser-pair-ab3.mjs`）：每个
构建两个副本，前两个实例是 A 组、后两个是 B 组，轮内顺序交替。每一组里都有
一个"先加载"的实例和一个"后加载"的实例，位置偏置在组内被平均掉，**空对照在
两个顺序上都读 1.0000**。语料在计时轮里重复 24 遍，一轮约 26 ms，量化降到
0.4%。

| 配对（四个实例，每个构建两个） | 最静窗口 | 逐轮比值中位数 |
| ------------------------------ | -------: | -------------: |
| 短文本的拷贝（batch 10）       |    0.75% |          0.37% |
| 同一个配对，两组换过来         |    1.14% |          1.10% |
| 同一个模块测四遍（空对照）     |    0.00% |          0.37% |
| 同一个空对照，两组换过来       |    0.00% |          0.34% |

#### 结论二：在 Node 里，两个构建必须放在两个进程里

Node 的同页面 harness 有同样的毛病：**比值会随着两个模块"列出来的顺序"变化
最多 2.5%，而且两个顺序的读数互相矛盾**（batch 9 那一轮的读数是 +2.53% / +2.47%
对 -0.05% / -0.52%）。原因也一样：两个模块的代码被编译进同一块代码空间，
地址不同，互相干扰。

**没有这个毛病的量法是一个构建一个进程**：进程自己加载模块、预热、渲染语料，
然后报进程的 CPU 时间（`process.cpuUsage()`）；驱动脚本把两个构建交替跑十轮，
取每个构建的"最静窗口"。空对照读 **±0.7%**。

| 配对（一个构建一个进程）     | 最静窗口 |    p10 |  中位 |
| ---------------------------- | -------: | -----: | ----: |
| 短文本的拷贝（batch 10）     |    2.18% |  3.45% | 3.65% |
| 同一个配对，两个构建换过来   |    1.92% |  2.66% | 5.05% |
| 同一个模块测两次（空对照）   |   -0.67% | -0.63% | 0.21% |
| 同一个空对照，两个构建换过来 |    0.31% | -0.35% | 0.61% |

两个顺序都说新构建快 2%–3%，而空对照是 ±0.7%。

| 产物体积                           | **-2,419 字节**                  |

原生侧中性是应该的：libstdc++ 会把三个字节的拷贝内联成几条指令，那里本来就没有
一次调用可以省。**WASM 侧的画像是佐证**：拥有这 12 个调用点的四个函数
（`AppendEm`、`FormatNumber`、`SetAttributeEm`、`Writer::build`）一共少了
36.6 ms 的 `__memcpy` 时间，整个流水线的 `__memcpy` 份额从 3.09% 落到 2.60%。

产物 md5 `86ef4757a3ed6375922e0e0321784985`（1,957,335 字节），两次独立构建
逐字节一致；imports 为空、exports 未变、固定线性内存 279 页（17.44 MB）。

### 第七轮增量：WebAssembly 上，已知长度的 `memcmp` 也是一次调用（2026-10-25）

上一条规则说"长度编译期已知 → 内联"。这句话对**拷贝**成立，对**比较**在
WebAssembly 上**不成立**：

> `wasm32-unknown-emscripten` 的 DataLayout 里没有 `a` 字段，也就是**不允许非对齐
> 访问**，于是 LLVM 跳过把 `memcmp` 展开成 load 的那一步，**调用被留了下来**。

渲染器对每个原子都要问好几次（节点的类、MathML 节点的标签、命令的名字），所以
模块里有 **302 个 `memcmp` 调用点，其中 197 个的长度是编译期已知的**。

`same_text`（`native/core/types.hpp`）于是**自己比较字节**：一次四个字节，用
load 和 compare，剩下不足四个的按字节比。

```cpp
template <size_t N>
inline bool same_text(std::string_view a, const char (&b)[N]) {
    constexpr size_t kLength = N - 1;
    if (a.size() != kLength) return false;
    const char* data = a.data();
    size_t i = 0;
    for (; i + 4 <= kLength; i += 4) {
        uint32_t left, right;
        std::memcpy(&left, data + i, 4);
        std::memcpy(&right, b + i, 4);
        if (left != right) return false;
    }
    for (; i < kLength; ++i)
        if (data[i] != b[i]) return false;
    return true;
}
```

那四个字节的拷贝只读文本里的那四个字节，**不会碰到文本外面**。跟着改了两处：

1. **比较"名字和一批名字"的辅助函数**（`oneof`，`native/core/mathml.cpp`）原来收
   一个 `initializer_list<std::string_view>`——**视图把字面量的长度藏起来了**，于是
   那次比较的长度只有运行期才知道。它现在是**变参模板**，字面量是**裸的**（不带
   `_u16` 后缀），每个字面量的长度都留在编译期。
2. **MathML 写入器的名字保持是视图**。`mml_text(...).value_or("")` 会造一个
   `std::string`（兜底值一次 `strlen`，有值时再拷一份），然后用 `find` 和
   `ends_with` 去找，**每一次都要再问一次 C 库那个字面量有多长**。现在名字是
   视图，查找的针也是视图。

| 测量                               | 读数                       |
| ---------------------------------- | -------------------------- |
| 模块里 `memcmp` 的调用点           | **302 → 53**               |
| `memcmp` 在 WASM 流水线里的份额    | **0.90% → 0.29%**          |
| Node，一个构建一个进程（最静窗口） | **+2.13% / +1.45%**        |
| Node，同上的 p10                   | +2.37% / +2.21%            |
| Node 的空对照                      | +0.03%                     |
| 浏览器，四个实例（最静窗口）       | **+1.36% / +2.28%**        |
| 浏览器，逐轮比值中位数             | +1.16% / +1.89%            |
| 浏览器的空对照                     | 0.00% / 0.00%              |
| 原生配对 A/B                       | 98.88% / 101.11%，**中性** |
| 产物体积                           | **+4,281 字节**            |

三处测量都说新构建更快，原生侧中性——原生构建里 libstdc++ 会把几个字节的比较
内联成几条指令，那里本来就没有一次调用可以省。模块变大了，因为每一次比较现在
都是内联的：WebAssembly 的税是**引擎生成的指令条数**，一次 load 加一次 compare
比一次调用便宜。

### 浏览器里怎么量 1% 的改动：同一页面里的两个模块

这一轮顺手把浏览器侧的测量补齐了。之前只有两种量法：

- **门禁脚本**（`tests/wasm/katex-browser-benchmark.mjs`）：KaTeX 对 VelociTex，
  两个引擎的噪声都在里面，这台机器上两次运行之间漂 ±5%。
- **core 直测**（`/tmp/browser-core-ab.mjs`）：只测核心，但**一次浏览器会话
  只测一个构建**，两个构建落在不同的负载窗口里。

新的 harness（`/tmp/browser-pair-ab.mjs`）在**同一个页面**里把两个模块各自
实例化（`WebAssembly.instantiate`，两个模块各有自己的线性内存，互不干扰），
直接调模块的导出（`vt_alloc` / `vt_render` / `vt_result_len` /
`vt_free_result`，和 npm 包的做法一样），每轮按 **A,B,B,A** 的顺序背靠背地测，
语料在计时轮里重复 8 遍。

**一个必须知道的坑：`performance.now()` 的分辨率是 100 µs，一轮 9 ms 的核心
就被量化成约 1.1% 一步。** 于是**逐轮比值的中位数分辨不出一%的改动**——两个
只差 1% 的构建，中位数会落在量化的某一步上，读 1.0000 还是 1.0106 取决于
顺序。**能分辨 1% 的估计量是"最静窗口"**（每个构建在所有轮里的最小值），
而且**两个顺序必须同向**。空对照读 1.0000，因为两个最小值落在同一步上。

| 配对（第二个是新的）       |     最静窗口 | 逐轮比值中位数 |
| -------------------------- | -----------: | -------------: |
| 任务栈（batch 9）          | 2.30%, 2.30% |   2.22%, 2.17% |
| 同一个配对，顺序换过来     | 1.14%, 1.14% |   0.00%, 0.00% |
| 同一个模块测两次（空对照） |        0.00% |          0.00% |

四个读数一致地说新构建更快（1.1%–2.3%），和 Node 配对 A/B 的 +1.30% / +1.90%
同向。

> **后来发现：这个 harness 有一个约 1% 的"实例位置"偏置，上表的空对照读
> 1.0000 是量化造成的巧合。** 原因与修法见"第六轮增量"一节的两个结论：
> **同一页面里的两个模块**要改用**四个实例**（每个构建两个副本），**Node 里的
> 两个模块**要改用**两个进程**（一个构建一个进程）。batch 10 的读数就是用那两套
> harness 量的。

**负结果：`em` 值的数字转换。** 长度的格式化（`AppendEm`，
`native/core/html/jsnum.hpp`）用四次除以十的链写分数的四位数字，用每位一次
除法写整数部分。换成"两位数字表"之后，分数变成两次互不依赖的除以一百加两次
查表。实测：

| 测量                   | 读数                                                                                         |
| ---------------------- | -------------------------------------------------------------------------------------------- |
| 原生配对 A/B           | 100.06% / 99.97%，空对照 99.61% → **中性**                                                   |
| Node 配对 A/B（60 轮） | +1.31% / -0.31%（**两序互相矛盾**）                                                          |
| 浏览器配对 A/B         | 两个顺序都把更好的最小值给了**第二个**位置（估计量的位置偏置），空对照 1.0000 → **分辨不出** |
| 产物体积               | **+793 字节**（表和更多的代码）                                                              |

**数字转换不是瓶颈**——瓶颈是值的缩放，那是一次 64 位乘法。这一处**没有发布**：
它低于项目要求的百分之一，而且模块还大了 793 字节。

### 两端引擎对同一处改动的反应相反（这一轮最重要的发现）

同一个源码状态的两份构建（第二批改动之前的那一份可以用
`/tmp/vtabl/core` 重建出来，产物的 md5 与当时发布的完全一致），在 Node 里用 V8 的
采样剖析器对比：

| 函数                        |   改前 |   改后 |        差 |
| --------------------------- | -----: | -----: | --------: |
| `__memcpy`                  |  1.41% |  4.59% | **+3.18** |
| `HtmlNode::WriteMarkup`     |  5.81% |  8.61% | **+2.80** |
| `ClassFlagOf`               |  2.08% |     —— |     −2.08 |
| `ClassList::ClassList(...)` |  1.33% |     —— |     −1.33 |
| `ParserState::Run`          | 10.63% | 10.48% |     −0.15 |

`ClassFlagOf` 与类名表的构造函数如预期消失了，但 `memcpy` 的份额涨了三倍多：
新的类名表是 64 字节（wasm32 里 12 个 4 字节指针 + 12 个长度），而它**按值**穿过
`MakeSpan`/`MakeSymbol`/`HtmlSpan` 三层，每一层都拷一次——在 WebAssembly 里，一次
固定长度的结构体拷贝会被 LLVM 变成一次 **libc++ 的 `memcpy` 调用**，而不是几条内联
的指令。原生侧同样的拷贝由编译器内联，所以原生没有这个代价。

改成右值引用之后每节点少两次拷贝，原生侧是中性，WebAssembly 侧省下两次调用。

**这一轮在两端的读数是相反的**：原生侧配对 A/B 读 **+5.0%**（两种顺序 95.29% /
95.42%，空对照 99.87%），而浏览器的 core 直测（语料在计时轮里重复 6 遍，一轮约
10 ms，避开 `performance.now()` 的 100 µs 量化）读**慢 3% 到 4%**。也就是说，**在
WebAssembly 里把结构体做大是要付钱的**：原生侧一次 64 字节的结构体拷贝是几条内联
指令，WebAssembly 侧是一次跨模块调用。同一条改动在两端可以有不同的方向，这一条
在写新的内核优化之前必须先知道。

**这一节的线索在下一轮兑现了。** `__memcpy` 涨上来的真正来源不是那次结构体改动的
**拷贝次数**，而是**拷贝的长度在运行期才知道**：`TagBuffer` 的每一个类名、每一个
开头标签，都是一次变长的 `memcpy`，在 WebAssembly 里就是一次 libc++ 调用。
把变长的拷贝换成定长的内联拷贝之后，浏览器的 core 直测从"慢 3% 到 4%"变成
"快 2.9% 到 8.0%"（见"第三轮增量"一节）。**教训是：在 WebAssembly 里，
"是不是 libc++ 调用"比"拷贝了多少次"更要紧**——一次长度已知的拷贝会被编译器内联，
一次长度未知的拷贝不会。

### 一个泄漏：一个页面渲染三万条公式就耗尽了堆

浏览器侧的长跑测试（3 万次以上渲染）会失败，报的是
`VelociTex UnexpectedToken: Unable to render formula.`——`vt_render` 里的
`catch (...)` 把 `std::bad_alloc` 一起吃了。**上一版已发布的产物也有这个缺陷**，
不是这一轮引入的。

定位的过程：

1. 原生侧驱动每渲染一条公式就打印一次常驻内存，看出它在稳定增长（每条约 320 字节）。
2. 换成"只解析不渲染"，增长变成 **0**——泄漏在 HTML 构建这一侧。
3. 覆写全局 `operator new`/`delete` 统计活体块，再对每个块记录分配点的回溯，
   直接抓到 `velocitex::generated::sqrtMainB5cxx11` → `MakeSqrtImage` →
   `BuildRadical`：**生成的 SVG 路径数据是一个 `std::string`，它被存进
   `HtmlPath::d_`——一个 arena 节点里的成员。arena 拥有这些节点，而且从不析构它们，
   于是这个字符串的堆缓冲永远不会被释放。**
4. 修法：路径数据改用 `ArenaText`（arena 里的文本），节点里不再有 `std::string`。
   顺带发现 `detail::CopyShort` 只覆盖文本的首尾各 24 字节（长度不超过 48 字节时
   才正确），路径数据有 585 字节，中间是个洞——所以补了 `CopyText`。
5. arena 扩容时退休的旧缓冲区也不再泄漏：`Reset()` 现在把它们释放掉。

修完之后，原生侧 200 轮（7,200 次渲染，每轮都渲染 HTML + MathML）的活体内存
**恒定在 1,192,747 字节，每渲染 0.00 个块**；浏览器侧 3 万次以上渲染的长跑测试
也通过了（上一版在同样的测试里失败）。这一轮唯一的性能代价是路径数据要拷进
arena，约 2%。

### 解析器的任务：每次转换还拷两次（2026-10-25 定位）

解析器的主循环把任务从栈里**取出来拷进局部变量**，再把后继任务**拷回栈里**，
一次转换搬两次 72 字节的结构：

```cpp
auto task = w.Tasks.back();   // ← 解析器最热的一行
w.Tasks.pop_back();
...
PushEdited(w, task, edit);    // ← 第二次拷贝
```

原生画像里这一行占解析器自己的 **19%**（`parser.cpp:1626`），WASM 画像里也是
解析器最热的一行，而解析器是整条流水线里最大的函数（12%）。

**后继任务就是任务本身改了几个字段**，所以"取出来"这一次拷贝是不必要的：任务
可以留在栈上就地改。但有两处不显然：

- **`Return` 标记必须跑在 continuation 的下面。** 标记先压栈、后继后压栈，
  栈顶是后继，所以后继先跑、`Return` 最后跑。任务留在栈上就没法往它下面压东西，
  这几种情形仍然要把任务取出再放回——拷贝只剩在这些情形里。
- **就地改的 edit 读的就是它写的那个任务。** lambda 写 `v.Field`、读
  `task.Field`，就地改的时候 `v` 就是 `task`，所以"先写后读同一个字段"的 lambda
  会读到新值。现有代码里有一处（`v.Last = result; v.Previous = task.Last;`），
  改成先读旧值即可。

### 已经做过的内核优化（全部保持逐字节一致）

- **已知长度的 `memcmp` 在 WebAssembly 上也是一次调用，于是比较改成自己比**
  （2026-10-25，`native/core/types.hpp` 的 `same_text`、`native/core/mathml.cpp`
  的 `oneof` 与 `mml_text`、以及 HTML 一族的字面量比较）：`wasm32` 的 DataLayout
  不允许非对齐访问，LLVM 于是跳过把 `memcmp` 展开成 load 的那一步，**调用留了
  下来**——模块里 302 个 `memcmp` 调用点有 197 个的长度是编译期已知的。`same_text`
  于是自己一次比四个字节（load 加 compare），`oneof` 改成变参模板好让字面量保留
  长度，MathML 的名字保持是视图（不再 `value_or` 造字符串，也不再 `find` /
  `ends_with` 问 C 库字面量有多长）。结果：模块里 `memcmp` 调用点 **302 → 53**，
  `memcmp` 的份额 **0.90% → 0.29%**，Node 的配对 A/B（一个构建一个进程）读
  **+2.13% / +1.45%**，浏览器的四实例 harness 读 **+1.36% / +2.28%**（空对照
  0.00%），原生侧中性，模块大了 4,281 字节。

- **逐字节的拷贝循环换成定长的移动**（2026-10-25，`native/core/html/markup.hpp`，
  `detail::CopyShort`）：处理一到三个字节的那一段是一个逐字节的循环，**LLVM
  认得这个模式，会把它换成一次长度运行期才知道的 `memcpy`**——在 WebAssembly 里
  就是一次 libc++ 的跨模块调用，而标记写入器每条公式要做几百次这样的拷贝。
  改成两次定长移动（先两个字节，三字节时再补一个）之后，模块里少了 **12 个
  `__memcpy` 调用点**，`__memcpy` 在 WASM 流水线里的份额从 **3.09% 降到 2.60%**，
  Node 的配对 A/B（一个构建一个进程）读 **+2.18% / +1.92%**，浏览器的四实例
  harness 读 **+0.75% / +1.14%**，原生侧中性。

- **变长的 `memcpy` 换成定长的内联拷贝**（2026-10-24，`native/core/html/markup.hpp`、
  `native/core/html/delimiter.{hpp,cpp}`）：开头标签在栈上的缓冲里拼出来，每个类名
  一次 `memcpy`，长度是运行期的，在 WebAssembly 里就是一次 libc++ 的跨模块调用。
  改成定长步进的 `detail::CopyBytes`（8/4/2/1 字节）之后，浏览器 core 直测
  **-2.9% ~ -8.0%**，原生配对 A/B **+1.3% ~ +2.4%**。分隔符那一族函数的
  `ClassList` 参数从按值改成右值引用（64 字节的按值传参同样是 libc++ 调用）。
- **MathML 的值池换成 `MarkupBuffer`**（`native/core/mathml.cpp`）：值池原来是一段
  `std::string`，每写一个值就是一次 `std::string::append`。在 WASM 里那是**一次
  调用 libc++ 的跨模块调用**（原生侧 libstdc++ 会把它内联，所以原生看不到差别，
  这也是它必须用 WASM 侧测量才看得见的原因）。换成 markup 缓冲之后，MathML 阶段
  在 WASM 里从 **13.49 µs 降到 12.09 µs（-10.4%）**。
- **MathML 的符号文本直接进值池**（`MmlNode::set_content_code_point`）：一个符号
  原来先生成一个 `std::string`（UTF-8 编码），再拷进值池；现在直接编码进值池。
- **字符串瘦身**（2026-10-24，`native/core/html/{delimiter,options,build_common}.cpp`、
  `native/core/macros.cpp`、`native/wasm/katex_wasm.cpp`）：四处热点每次渲染都在
  造字符串，现在都不造了——
  - `RetrieveTextFontName` 原来返回 `std::string`（`base + "-" + style`，两个拼接），
    现在返回一张 16 项的静态表里的视图；只有family 是自定义的时候才拼一次。
  - 分隔符的字体名（`Size1-Regular`…`Size4-Regular`）是一张静态表，
    `svg_label` 是 `const char*`，`MakeGlyphSpan` 的尺寸类名是视图。
  - 宏展开的根作用域标记原来把**整个源串拷贝两遍**（`LexToken(std::u16string, …)`
    按值收参再 `make_shared`），现在用一个共享的空串当标记。
  - WASM 入口的 UTF-8 解码原来逐字符 `push_back`（每次都查容量），现在直接写进
    缓冲区，ASCII 连续段单独处理。
  - **确定量的效果：每公式的堆分配从 22.53 次降到 13.78 次（-38.8%）**；
    墙钟上这一组读数是 -1% 到 -4%（两个顺序都指向同一个方向，见上面的方法学一节），
    浏览器门禁的中位轮从 2.0–2.2 ms 降到 1.9–2.0 ms。
- **HTML 构建器不再为每个符号生成临时字符串**（`native/core/html/build_html.cpp`）：
  符号的文本写进一个栈上的 `char16_t[2]`（`ToScalar`），数学类名直接用渲染器的
  字面量（`AtomClass` 返回 `const char*`，之前每次都包了一层 `std::string`）。
  原生侧无差别（libstdc++ 会内联），WASM 侧因为少了 libc++ 的调用而变快。
- 两项合计（v24 → v26）：WASM 整条流水线 **-2.50% / -2.33%**（两次 500 轮配对
  测量，空对照 +0.12% / +0.14%），浏览器端 3.04× → 3.08×。
- **HTML / MathML 直接写入自有的 `MarkupBuffer`**（`native/core/html/markup.hpp`）：
  一条公式的 markup 由几百个短片段拼成，`std::string::append` 每个片段都要调用一次
  `memmove`；在 WASM 里这次调用的开销远大于拷贝本身。新的缓冲区把短片段内联拷贝，
  **WASM 的 HTML 阶段实测下降 35%（54 → 43 µs/公式）**，MathML 阶段同步下降。
- **DOM 节点改用 bump arena 分配**（`native/core/html/domtree.cpp`）：一棵树有近百个
  节点，逐个堆分配的开销大于节点本身；arena 让节点连续，序列化时也顺带改善了
  局部性。HTML 阶段的堆分配从每公式约 400 次降到约 80 次。
- **DOM 树的所有向量也改从 arena 取内存**（`ArenaAllocator`）：子节点列表、
  构建器的子节点下标表、样式声明与属性都不再走堆分配，释放整棵树时也不再
  逐个归还。HTML 阶段从每公式 200 次堆分配降到 83 次。
- **样式声明、vlist 元素与 `CssStyle` 对象也搬进 arena**：样式声明表原本是
  `std::vector`（默认分配器），每条公式要申请几十次；现在全部走 arena，
  HTML 阶段从每公式 89 次堆分配降到 31 次。
- **MathML 的写入器跨渲染复用**（`native/core/mathml.cpp`）：节点表、属性表与
  值池改成线程局部静态对象，每次渲染只清空内容、保留容量；值池里的字符串
  也不再重复分配。MathML 阶段从每公式 20 次堆分配降到 11 次。
- **MathML 不再为每个字符造一个字符串**：UTF-8 编码直接写进调用方的缓冲区，
  遍历用的栈也改成线程局部复用。MathML 阶段实测 9.4 → 5.7 µs/公式。
- **尺寸类名不再走 `to_string` + 临时 vector**（`HtmlOptions::AddSizingClasses`）：
  `reset-size6`、`size6` 这类名字直接写进调用方的栈缓冲区。
- **WASM 侧缓存选项 JSON**：一份文档里的所有公式带的是同一份选项，
  现在只解析一次，之后直接复用已编码的字节。
- **样式与属性名改成 `string_view`**：这些名字都是 KaTeX 写死的字面量，
  声明时不再拷贝名字。
- **类名列表改成单个空格分隔的字符串**（`ClassList`）：KaTeX 的类名数组在写
  markup 时才 join，节点本身不必在堆上放一个 vector；查类名也从逐元素比较变成
  一次扫描。扫描逐字符比较，遇到第一个不同的字符就结束，因此查一个不存在的
  类名不再要扫完整个类名；第一个类名的长度被缓存下来，取它不用再扫描。
- **WASM 开启 `-flto`**（`native/build-wasm-katex.ps1`、`native/build-wasm-core.ps1`），
  单次 html 渲染实测下降 10–23%。
- **宏展开器改成单次查表**：展开循环原本对每个 token 跑 12 次线性扫描
  （`OneOf(name, {...})`），现在一次开放寻址查表返回命令标志位。
- **字体度量查表 O(1)**：原先 `RawMetric` 每次渲染字符都要线性扫描该字体的度量表
  （最多 276 项 × 44 B ≈ 12 KB 的内存扫描），现在建一次索引直接命中。
- **符号 / 命令 / 宏查表 O(1)**：原先每次查表都走 `std::hash<u16string_view>`
  的逐字节 murmur 哈希 + 桶查找，现在单字符走直接表、命令走自建开放寻址表。
- **逐 token 的命令链改成有序表**：重音、可伸缩箭头、字体命令原本是每次解析都
  走一遍的线性比较链，现在查有序表；有序表就是这些命令的唯一真值来源。
- **token 缓存源文本指针**：读 token 文本从两次依赖载入降到一次。
- **复用 document / 节点 arena / 输出缓冲**：不再每次渲染都重新分配
  `MathDocument`、语义节点向量与 HTML / MathML 字符串，浏览器端 WASM 侧
  线性内存不再增长。
- **MathML 节点瘦身**：`MmlNode` 从 ~1.3 KB 压到 ~90 B（紧凑属性表 + 共享值池），
  MathML 阶段下降约 25%。
- **npm 胶水层**：直接从模块内存解码结果、缓存模块内存视图、选项 JSON 就地拼接，
  去掉第二次字符串拷贝。
- **payload 不再二次拷贝**：HTML 与 MathML 原本先写进 document 自己的缓冲区，
  再拷进最终 payload——每公式约 7 KB。WASM 里的 `memcpy` 是逐字节循环，
  这次拷贝并不便宜；现在 markup 直接写进结果缓冲区。
- **`makeEm` 只做一次 64 位除法**：原来 `% 10000` 与 `/ 10000` 各一次，
  除法在 WebAssembly 里是真指令。
- **`makeEm` 走 32 位快路径**（`native/core/html/jsnum.hpp`）：缩放后的值能放进
  32 位时，除以常数与取余数都在 32 位里算。WebAssembly 没有 64 位的高位乘法
  指令，除以常数会被展开成十几条 32 位指令，这一处改动让
  **WASM 构建整体下降约 9%**。
- **HTML 的 DOM 节点不再走虚函数分发**（`native/core/html/domtree.hpp`）：
  节点的种类变成一个普通字段，写节点时按种类分支，编译器可以把常见种类的
  写法内联进递归里。一条公式要写近百个节点，每次经虚表跳转都不便宜。
- **样式里的 `em` 长度按数字存**（`CssStyle`）：`makeEm` 的结果在声明写进
  markup 时才生成，长度不需要先变成字符串，样式声明也不再带一次堆分配。
- **语义节点直接在树里构造**（`native/core/parser.cpp`）：一个语义节点有三百多
  字节，原来先在栈上建好、再搬进树里、再搬一次；现在一次构造到位。
- **类名表的方法放进头文件**（`ClassList`）：渲染器要为每个节点问好几次
  类名，名字在调用点是常量，内联之后编译器能省掉长度检查。
- **子节点表先计数再分配**：`Builder::Children` 与 `ModuleContext::Children`
  先数一遍子节点数量，arena 里一次分配到位，不再按 1→2→4 的步长反复申请并拷贝。
- **`IsWhiteSpace` 内联**：词法器、宏展开器和解析器对每个字符都要问一次，
  跨编译单元的调用比判断本身还贵。
- **分隔符改用 `string_view`**（`native/core/html/delimiter.cpp`）：
  分隔符的名字都是符号表里的字面量，比较从调用字符串类变成 memcmp，
  上下左右箭头、括号这些部件也不再各自复制一份字符串。
- **类名查询改成位掩码**（`ClassList`）：渲染器只问十来个固定的类名
  （`mbin`/`mrel`/`mspace`/`mtight`/`nobreak`/`enclosing`/`katex-tag`/`allowbreak`/
  `mathnormal`/`katex-newline`），类名表为它们各留一位，问一次类名就是一次位测试，
  不再扫描类名。实测 **-1.3%**。同时把类名表的计数语义对齐 KaTeX
  （KaTeX 的数组长度是类名个数）。
- **DOM 树整体搬进 arena**（`native/core/html/domtree.hpp`）：节点、节点的文本、
  类名、样式声明值与属性值全部从 arena 取内存，节点不再拥有任何堆内存，
  也不再需要析构（`ArenaDeleter` 是空实现，保留 `unique_ptr` 的 API 形态）。
  一条公式的节点从 97 次堆分配降到 0 次。实测 **-6.5%**。
- **token 改为移动而非拷贝**（`native/core/macros.cpp`）：宏展开器把 token 压进
  待处理栈时不再拷贝引用计数，实测 **-1.2%**（42.7 µs）。
- **查表按首字符短路**（`native/core/macros.cpp`、`native/core/parser.cpp`）：
  命令表、宏表与展开命令表里，多字符的名字全部以 `\` 开头，其余都是单字符。
  于是展开器与解析器在处理一个普通符号时不必再算一次哈希：展开命令表的单字符
  走直接表，命令表与内置宏表对"多字符且不以 `\` 开头"的名字直接返回未命中。
  一条公式的 token 里绝大多数是普通符号，这一项把解析阶段压低 **4.1%**。
- **语义节点的访问不再做范围检查**（`native/core/parser.cpp`）：解析器每走一步都要
  取一个节点，`at()` 的检查比取值本身还贵；下标是解析器自己发出来的，去掉检查
  之后解析阶段再降 **3.6%**。
- **字符的 script 查询按范围短路**（`native/core/parser.cpp`）：KaTeX 只给少数几个
  字符标 script，最小的是 U+00B2，所以 ASCII 字符永远没有 script——解析器对每个
  普通符号都问一次，此前每次都要构造一个 `optional<u16string>`。现在 ASCII 直接
  返回"没有"，而且因为调用方只判断"有没有"、从不取值，返回值也换成了 `bool`。
- **表达式的结束判断先看首字符**（`IsEndOfExpression`）：只有控制序列与 `&`
  才可能是表达式的结束，先看首字符省掉了每个 token 的四次字符串比较。
- **矩阵单元不再拷贝环境名与任务**（`AddMatrixCell`）：环境名只读不写，改成引用；
  任务从按值传参改成按引用传参，省掉一次 `optional<u16string>` 的拷贝
  （`smallmatrix` 这类名字会触发堆分配）和一次 88 字节的任务拷贝。
- **MathML 的序列化复用遍历栈**（`native/core/mathml.cpp`）：写入树的遍历栈早已是
  可复用的线程局部对象，但把节点写成 markup 的那一步每次渲染都新建一个局部
  vector（一次堆申请与释放）。现在两边都用可复用的栈。
- **MathML 与 HTML 共用同一张转义表**：KaTeX 在 MathML 与 HTML 里转义的字符与
  实体完全相同，MathML 那边却是对每个字符做五次比较；现在两边都用 HTML 的
  256 项查表，一次查表回答一个字符。
- **MathML 的节点文本按视图传递**（`node_text`）：为了做一次比较而构造一个
  `std::string`，现在返回的是值池里的视图。
- **与 UTF-16 字面量的比较全部改用编译期长度**（`native/core/types.hpp` 的
  `_u16` 后缀，770 处调用点）：`std::u16string_view(const char16_t*)` 会调用
  `char_traits<char16_t>::length` 求长度，而那是逐字符的循环。**GCC 没有针对
  `char16_t` 的常量折叠**，于是每一次与裸字面量的比较都要在运行时把字面量扫一遍
  ——实测这一项占解析阶段的 **36%**（行级 profile 里 `char_traits::length` 的
  样本占比 35.8%）。加 `_u16` 后缀后，视图的长度在编译期已知，比较变成
  "长度检查 + 展开成直线指令的逐字符比较"。实测 **解析阶段 11.1 → 6.3 µs（-43%）**、
  **原生整条流水线 40.3 → 34.0 µs（-16%）**。clang 自己会折叠字面量的长度，
  所以 WebAssembly 侧不吃这一段；但同批改动里的第二部分（等宽字体的连字表、
  词法器的 `\verb` 判断、重音的可选文本、颜色归一化）**在 WebAssembly 上值 2.4%**。
- **格式化出来的数字不再向堆要内存**：`makeEm` 与属性长度都 `reserve(16)`，
  比 `std::string` 的小缓冲区大一个字节，于是每个格式化长度都把小缓冲区丢掉、
  去堆上要同样多的字节——**每公式 3.8 次分配**。去掉之后每公式的分配次数从
  **11.5 降到 6.9**，WebAssembly 上值 0.5–1.5%（glibc 的 `malloc` 足够快，
  原生上看不出来）。
- **MathML 的节点压进一个 cache line，值池扁平化**（2026-10-23，v23）：
  MathML 写入器是整个内核里对 WebAssembly 最敏感的一段（下面单独一节）。
  三处改动：节点的属性表从 8 个槽改成 6 个（语料里最忙的节点——颜色框——正好 6 个
  属性，溢出的向量从未被走到）并去掉节点里的 `std::vector` 成员，节点从 **96 字节
  降到 64 字节**；属性值与元素文本从"每值一个 `std::string`"改成**一个连续缓冲 +
  偏移表**（每公式约 23 个值）；`variant()` 返回字面量的视图而不是构造一个
  `std::string`（每公式被问 **17.6 次**）。
  实测：**MathML 阶段原生 6.09 → 5.52 µs（-9.4%）**、WASM 12.55 → 11.70 µs（-6.8%），
  整条 WASM 流水线 **-1.8%**（配对中位数，1000 轮），原生整条流水线 gcc -1.1% /
  clang -1.9%。逐字节一致保持 5411/5411。
- **markup 缓冲用宽存储拷贝片段**（2026-10-23，v24）：编译器把 `"<span"` 的 5 个字节
  写成了 **5 次单字节存储**（反汇编可见），而一个公式的 markup 是 1262 段片段。
  现在一段片段用**两次重叠的宽存储**拷贝：前一次盖住头部、后一次盖住尾部，
  **既不越界读也不越界写**。实测原生 HTML 阶段 19.58 → 18.95 µs（**-3.2%**），
  WASM 整条流水线 **-1.9%**（配对中位数）。在 WebAssembly 上更值钱，因为那里的
  每次字节存储都比原生贵。

  > 这一条此前被记在"已经排除的方向"里（"分段拷贝：无差别，原生慢 1%"）。那次读数
  > 出自**输入缓冲过小**的 harness——公式提前失败，拷贝根本没跑到。换成有效 harness
  > 与配对估计量后，它是正收益。

### MathML 写入器：整个内核里对 WebAssembly 最敏感的一段

MathML 阶段在 WASM 下比原生慢 **83%**（HTML 是 40%，解析器持平），
所以它是浏览器 5× 目标上最值得动手的地方。用 `__rdtsc` 把这 6.4 µs 拆开：

| 阶段       | 占 MathML 阶段 | 做什么                                           |
| ---------- | -------------: | ------------------------------------------------ |
| 前置遍历   |            15% | 算样式、尺寸、颜色、父节点                       |
| **建图**   |        **50%** | 每个语义节点生成一个 MathML 节点、记属性、记值池 |
| **序列化** |        **35%** | 遍历这张图写 markup                              |

每公式的规模：**32 个 MathML 节点**、31 次属性写出、23 个进值池的值、
17.6 次 `variant()`、26.7 次转义。行级 profile（`perf` + `addr2line`）里
最热的三行是序列化时**把节点的 8 个属性槽拷进一个局部数组**（4.6%）、
建图时的**语义树遍历**（2.1%）与**样式计算**（2.2%）——前两条都是
_取内存_ 的开销，而不是计算。

这解释了 v23 那一步为什么有效：WebAssembly 引擎对**追指针的数据结构**最不友好
（地址是 32 位，而且引擎要给每次访问做边界检查），而 MathML 写入器做的正是这件事。
把节点压进一个 cache line、把值池变成一段连续内存，收益（-6.8%）明显大于
原生（-9.4% 的阶段收益换算到总流水线只有 -1.1%），**说明瓶颈确实在内存访问
而不在算法**。

剩下的路是**边建边写**（不再建图），但 KaTeX 的 `buildMathML` 里父节点的属性
依赖子节点的属性（`isNumberPunctuation` 要看子节点的 `lspace`/`rspace`，
`mathvariant` 要和相邻节点比较），所以属性表不能直接省掉，只能改成
"用到时按需重算"——这是一次重写级改造，收益上限是这 35% 的序列化加上
建图里的内存流量。

### HTML 阶段：同样的方法，量出来的结构

HTML 阶段（原生 18.9 µs，WASM 26.0 µs）用同一套方法拆过，行级 profile
（`perf` + `addr2line`，只测 HTML 阶段的基准）：

|  占比 | 热点                                               |
| ----: | -------------------------------------------------- |
| 14.7% | **markup 缓冲**（逐字节拷贝 9.1% + 容量检查 4.5%） |
|  4.8% | **节点 arena 的 bump 分配**                        |
|  2.4% | 建树时的语义树遍历（`build_html.cpp`）             |
|  1.7% | 节点的构造（arena 里的 placement new）             |
|  1.5% | 数字格式化（`jsnum.hpp` 的逐位十进制）             |
| ~0.8% | 符号查找（`unordered_map`）                        |

第一项就是 v24 改掉的那一处——**14.7% 里最大的一块是"把字节一个一个搬过去"**，
而反汇编显示编译器确实就是这么做的。

DOM 的内存结构与 MathML 的图是同一类问题：**每个节点不是一个自包含的块**。

| 结构         |                          尺寸 |
| ------------ | ----------------------------: |
| `HtmlNode`   |      152 B（3 个 cache line） |
| `HtmlSymbol` |                         200 B |
| `ClassList`  | 24 B（文本另在一块 arena 里） |
| `CssStyle`   | 24 B（声明另在一块 arena 里） |

序列化每个节点要碰 5 块内存：节点本身、类名文本、样式声明、子节点向量、属性向量。
这正是 WebAssembly 引擎最不擅长的形态（地址 32 位，引擎还要给每次访问做边界检查）。
MathML 那边把节点压进一个 cache line 就拿到了 -6.8%，HTML 这边的对应改造
（把类名表与样式内联进节点、或者干脆边建边写）是下一步最大的单点。

### WASM 税不是边界检查（2026-10-24 的更正）

这份文档此前反复说「WASM 的每次内存访问都要带边界检查，所以税在内存访问上」。
**这句话是错的**，或者至少是错在因果上。实测：

- **产物里根本没有边界检查。** 已发布模块的反汇编（26 MB 文本）里只有 **1 处**
  `memory.size`；通过运行期地址的存储长这样，没有检查：
  `(i32.store8 (i32.add (local.get $4) (local.get $6)) ...)`。
  检查是**引擎**在把模块编译成机器码时插进去的，编译 wasm 的那一步不产生它，
  所以在二进制里看不见。
- **检查是真的，但它不是税。** 一个微基准（每轮一次存储 + 一次读取，加一条编译器
  屏障防止被折叠）：

  | 访问方式           |     原生 |  WebAssembly |
  | ------------------ | -------: | -----------: |
  | 静态数组，索引任意 | 0.285 ns | **0.319 ns** |
  | 运行期指针         | 0.283 ns | **0.512 ns** |

  原生侧两种写法**没有差别**；WebAssembly 侧经指针的访问贵 61%，因为引擎必须
  检查地址；访问静态数组则不用检查，因为引擎知道数据段在内存里。

- **但这笔账加不起来。** 一个公式的 markup 是几百次访问，全部加起来只值 WASM
  流水线 47 µs 里的约 0.2 µs，也就是 **0.5%**。所以 1.8× 的税**不是**检查，
  而是引擎生成代码时的**指令条数**。要付掉它只能**少干活**，而不是少碰地址。
- **这个规律留给重写用。** 在 WebAssembly 里，**用具名静态数组**访问的结构是便宜的，
  **经指针**访问的结构是贵的。所以扁平 HTML 渲染器应该用**偏移量**去寻址
  arena 里的节点，而不是用指针。
- **按这个规律做过的实验（没有发布）**：把 WASM 构建的 markup 缓冲换成静态数组
  （1 MB；语料里最大的 markup 是 35 KB），MathML 值池的缓冲另给一块自己的存储。
  按计数是每公式少了几百次引擎检查（**0.5%–0.9%**），**时间落在测量噪声里**
  （Node 配对 A/B 两序读 -0.34% 与 +4.27%，浏览器 core 直测略偏向新构建）。
  **没有发布**：低于项目要求的 1%；模块的线性内存多占 1 MB（295 页 vs 279 页）；
  而且它给公式大小加了一个原生构建没有的上限。

### 已经排除的方向（都做过 A/B 实测，不要重试）

- **`MarkupBuffer::Append` 的十六字节快路径**（把短片段的内联拷贝拆成一个小的
  热路径，长的走一个不内联的函数）：**原生侧更快**（配对 A/B 两种顺序 +1.9% /
  +1.3%，空对照 99.74%），**Node 里的 WebAssembly 也更快**（两种顺序 +0.5% /
  +4.0%，逐轮比值的中位数 +1.6% / +5.8%），**但浏览器里更慢**——core 直测六对，
  最快一轮的中位数 **-1.5%**、中位轮的中位数 **-4.7%**、均值的中位数 **-4.8%**。
  按本项目的规矩（"只发布在浏览器里测得出效果的改动"）**回退**了。
  这也是"Node 里的读数不算结果"的又一个例子：原生与 Node 同向，浏览器反向。
- **`makeEm` 的格式化结果缓存**（2026-10-24 重做，**没有发布**）：
  一条公式要写 43 个 `em` 长度，"把长度文本记下来"看起来是显然的优化
  （数字的格式化是写一条样式声明里最贵的一步）。实验的结论是相反的，
  原因值得留着：
  - **这些值几乎都不相同。** 基准的 36 条公式的**舍入后**长度是 320 个不同的数，
    平均每条公式 20 个，所以一张文本表最多只能回答一条公式 43 次调用里的 79%。
    实测：按 double 的**原始位**做键，命中率 32%（这些 double 的低位不同）；
    按**舍入后的值**做键，命中率 68.6%（256 项）或 28.1%（64 项、每条公式一代）。
  - **命中也要先算出那个值。** 表的键必须是舍入后的值，而舍入后的值正是缩放那一步
    算出来的——所以命中时缩放照样要付。缓存只能省下**取数字**那一步，
    而实际出现的值都很小（整数部分只有零或一，取数字的循环跑一两次），
    约二十个周期；查一次表的成本与之相当。
  - **实测一致。** 原生配对 A/B 两序读 100.74% / 99.63%（同窗空对照 100.15%），
    Node 的 WASM 配对读 -0.55% / +2.29%。中性，按规矩不发布。
  - **实验里挖出来的两个缺陷留下了**：`AppendEm` 的罕见路径（无法精确缩放的量级）
    会把样式声明的分号丢掉，那条声明就没有结束符了；数字拷贝那一句在
    `-Wstringop-overflow` 下报警，因为编译器看不出整数部分最多十五位。都已修。
- **把类名表先拼进栈上的缓冲再一次性写出**（2026-10-24 实测）：
  动机是"每次写 markup 都要一次调用，调用次数是乘数"——这条规律在输出缓冲还是
  `std::string` 时成立，现在缓冲已经是 `MarkupBuffer`，一次写就是一次容量检查
  加一次内联拷贝。改完之后**每公式的写次数从 624.8 降到 547.4（-12.4%）**，
  但**时间没有变**：原生配对 A/B 读 -0.46%（噪声内），Node 侧两种顺序互相矛盾
  （一轮 +0.36%、另一轮 -2.04%），浏览器侧同样读不出来。
  **这条规律已经过时了**——现在该找的是"是不是一次运行时的调用"，不是"写几次"。
- **把 `MarkupBuffer` 的片段拷贝强制内联**（`[[gnu::always_inline]]`）：
  片段拷贝的调用点有几十处，每次写 markup 都要过它一次。强制内联之后
  模块只大了 6 KB（+0.3%），但浏览器 core 直测**读不出来**（最快一轮与中位轮
  在噪声内互相抵消），原生侧也读不出来。**没有发布**。
  这和"十六字节快路径"那条结论一致：这一块对代码体积敏感，浏览器比 Node 更敏感。
- **让 arena 上的子节点向量预留四个位置**（2026-10-24 实测，**没有发布**）：
  向量按倍增增长，每增长一次就把子节点复制到 arena 的新块里，而长度只有运行时
  才知道的复制在 WebAssembly 里是一次 `libc++` 的调用。
  **确定性的计数确实好了**：每公式的 arena 分配从 **261.4 次降到 244.7 次**
  （-6.4%），省掉的 16.7 次各带一次 `memcpy`。
  **但是时间没有动**：原生配对 A/B 读 +0.35% / +0.64%（空对照 ±0.6%），
  Node 的 WASM 配对读 +0.59%（空对照 ±0.7%），浏览器读不出来。
  它要把 `NodeVector` 从一个类型别名换成一个类（一个核心容器的改动），
  换来的却读不出来，**按"只发布测得出效果的改动"的规矩回退了**。
  顺带记下一条：**画像里的 `memmove` 只有 2.25%，其中向量增长那一部分更小**——
  arena 的 bump 分配很快，复制也很短。
- **把 arena 的足迹翻倍**（2026-10-24 实测，**没有发布**）：
  动机是"每个公式的 HTML 树有 38 KB，一次公式渲染把它整个走一遍，而 L1 只有
  32 KB，所以缓存未命中才是 `NodeArena::Allocate` 占 2.64% 的原因"。
  **探针是行为等价的**：给 `HtmlNode` 加 128 字节填充（节点从 240 字节到 368
  字节，arena 的足迹从 38 KB 到 71 KB，**+87%**），其余一个字不改，
  输出的 markup 逐字节相同。
  **时间没有动**：原生配对 A/B 前向读 99.39%（填充版慢 0.6%），
  反向读 101.13%（填充版快 1.1%），**两序矛盾**，而同窗的空对照读 100.55%。
  也就是说 **+87% 的足迹换不到 1% 的时间**——"arena 的足迹"这条假设不成立，
  `NodeArena::Allocate` 的那 2.64% 不是缓存未命中。
  这一条把"把类名表缩小、把节点缩小"一整类想法划掉了：
  **HTML 树的内存足迹不是瓶颈**，再省也省不出时间。
- **同一个探针在浏览器里说的正好相反**（2026-10-25 实测，**没有发布**，是修正）：
  上面的探针是在**原生构建**上跑的，而目标是浏览器。`-DVELOCITEX_PAD_NODES`
  （这个开关在 `native/core/html/domtree.hpp` 里）给节点加 128 字节填充，**四实例**
  harness 读它**慢 2.46%**（正序）和**慢 1.35%**（反序），空对照恰好 1.0000。
  也就是说：**一个公式的 HTML 树在浏览器的缓存里放不下**，节点的每一个字节都要付两次
  ——建的时候写一次，走的时候读一次。
  **所以"把节点缩小"这一族想法在原生上是死的，在浏览器上是活的。** 值得试的有两条：
  - **类名表是节点的 112 字节里的 112 字节**（240 字节的节点里；WebAssembly 里指针是
    4 字节，所以是 192 字节的节点里的 64 字节）：12 个指针加 12 个长度。改成一张名字
    表的**下标**，只要 16 字节。
  - **children 和 attributes 是两个向量**，占 48 字节，而多数节点两样都没有：挪进一张
    带下标的旁表，只要 8 字节。
    判定这两条的是**浏览器探针**，不是原生配对 A/B：一个在原生上中性的改动，在浏览器里
    仍然可能值一个百分点。
- **`-mbulk-memory`**：默认构建里**一条 bulk memory 指令都没有**（`wasm-dis` 查过），
  也就是说 WASM 的每次 `memcpy`/`memmove` 都是逐字节循环。但打开之后并没有变快：
  交替 A/B 两次分别落在 -0.9% 与 +1.7%，而 null test 的噪声就有 ±0.9%——
  拷贝的次数少、长度短，开销在于**调用 libc++ 本身**而不在循环。
  既然没有收益，就不值得为它加上浏览器对 bulk memory 的支持要求。
  **2026-10-24 用新的"每组全局最小值"估计量重测了一遍**（`/tmp/wasmmin2.mjs`：
  对每组取所有轮次、所有重复里的最小值，也就是两个构建各自最安静的那次窗口）：
  逐组中位比值 99.8%–103.1%，两种顺序给出的方向相反——**仍然是噪声**，
  与上面的结论一致。**`-msimd128`（连同 `-mbulk-memory`）同样是中性**：
  逐组中位比值 99.8%–103.1%，没有发布。
  **2026-10-24 又在当前的核上重测了一次**（单开关的干净 A/B：只有 bulk memory
  这一个开关不同）：Node 的"最静窗口"两序读 +1.98% / +0.14%，而同窗的空对照
  读 +0.46%（扣掉之后是 +1.52% / -0.32%）；浏览器的 core 直测 8 对，最快一轮
  的配对中位比 0.984（+1.6%），中位轮的配对中位比 0.918（+8.3%，但那一列
  会被离群轮污染）；浏览器门禁看不出差别（两版都是 3.64×）。
  画像给出的上界是 2%（被取代的 `__memcpy` 1.25% + `memmove` 0.77%），
  实测落在这个上界之下。**结论不变：不开**，而且它会给发布的模块加上一项
  WASM 特性要求（Chrome 75 / Firefox 79 / Safari 15）。
- **固定线性内存**（`-sALLOW_MEMORY_GROWTH=0`）：这是本轮最大的单项效应，
  而且**它是 Node 侧 V8 的假象**。内存可以增长的模块声明为 `(memory 256 32768)`
  （初始 16 MB，最大 2 GB），关掉增长之后声明为 `(memory 256 256)`；
  用固定声明的构建在 Node 里快 **56%**（400 轮配对的中位数，把两个构建的顺序
  反过来再测一次同样成立；去掉 JS 解码的探针读到的也是 -56%，所以效应在内核里），
  **但浏览器里完全没有**（同一构建 3.25× 对上一版的 3.23×）——Chrome 不走 Node 走的那条路。
  因此没有发布。固定成 64 MB 更弱：Node 里只有 -3.05%，因为 V8 会把模块的
  外部内存计入，回收更频繁。
- **`-sMALLOC=emmalloc`**：模块的分配器在 profile 里占 1.3%，但换成 emmalloc
  之后是 **-0.01%**（800 轮配对），不值得。
- **原生构建的 9% 花在动态 TLS 上（2026-10-24 实测，浏览器侧没有这项）**：
  原生构建是一个 `.so`，由 .NET 通过 `dlopen` 装载，于是每个 `thread_local`
  的访问都要走一次 `__tls_get_addr` 的 PLT 调用。原生画像里这一项占
  **7.26% + 1.80%（plt）= 9.06%**，热点是热路径上的 `thread_local`：
  `html/domtree.cpp` 的节点 arena（**每公式约 300 次 bump 分配**）、
  `html/options.cpp` 的字体度量、`html/build_common.cpp` 的符号信息。
  **WASM 构建没有"取地址"这一项成本**：Emscripten 在没有 pthread 时把 `thread_local`
  编译成普通全局（编译产物里没有 `__tls_get_addr`、没有 TLS 段）。
  **但 WASM 构建仍然要付"初始化守卫"这一项**：一个 `thread_local` 的类型只要有
  构造函数或析构函数，每次访问都要先调用运行时的 `__tls_init`；原生构建里这是
  一次 `__tls_get_addr` 的 PLT 调用加一个分支，WASM 构建里是一次真实的函数调用。
  **2026-10-24 这一项被修掉了**（见"v35"一节）：把复用的状态改成命名空间作用域的
  对象，WASM 侧读 **+4.45%**，浏览器 core 直测最快一轮 **-5.2%**、中位轮 **-4.0%**。
  修掉之后**这一项在两侧都不再是成本**，原生/.NET 独有的那 9% 仍然是。
  没有把 arena 改成"每次渲染解析一次"的上下文的原因：唯一干净的办法是沿着整条
  HTML 构建链传下去（`build_html.cpp` 1,980 行 + `build_common.cpp`
  806 行 + accent/array/delimiter/enclose 四个模块，`operator new` 拿不到上下文）；
  另一条路是 `-ftls-model=initial-exec`，但那会让 `dlopen` 依赖静态 TLS 余量，
  对一个被 .NET 装载的库来说是部署风险。
- **包这一侧的 JavaScript 已经到地板了**（浏览器里单实例、配对分层）：
  核心 44–52 µs、JS 那一层（胶水 + 包自己那层）6–7 µs，整条路径 50–62 µs。
  JS 那一层里 0.42 µs 是解码（字节必须变成字符串，省不掉），1.2–1.4 µs 是编码
  源文件，0.46 µs 是选项的 JSON，其余是 promise 与结果对象。
  三条"再省一点"的路都量过，**一条都不划算**：
  - **promise 是免费的**：去掉内层 `compile` 的 promise 的那一版，与原版
    **0.00%**（同一页面里两个入口变体配对 A/B，150 轮，A,B,B,A）；
    把 `async function` 换成返回 promise 的普通函数也是 **0.00%**。
    之前"promise 花了 2 µs"那次测量是**量错了**：它比的是一个被 await 的
    异步函数和一个被 await 的同步函数，量到的是 await 本身。
  - **解码不挑字节住在哪儿**：从 WebAssembly 内存里解码 0.19 µs，
    从内存外的缓冲区里解码也是 0.19 µs；先把 payload 拷出去再解码**更贵**。
    平台的 `TextDecoder` 对可增长（resizable）的 `ArrayBuffer` 也不慢
    （Node 里 245 字节 0.48 µs 对 0.38 µs）。
  - **选项不贵**：JSON 0.5 µs，周边的检查更少。
    **整层的上限**：即使 JS 那一层归零，也只从 3.2× 走到约 3.5×，
    到不了 5 倍——所以这一层不再是投入的对象。
- **类名表一次成型**（把整个类名表先拼进栈缓冲再一次性写进 arena，
  取代"每个类名一次分配"）：单类名列表占多数，多出来的一次拷贝比省下的分配更贵，
  实测 **+3.4%**（42.6 → 44.1 µs），已回退。
- **样式键改用内联逐字符比较**（代替 `string_view` 的 `memcmp`）：键很短，
  `memcmp` 的向量化实现更快，实测持平偏慢，已回退。
- **类名的位掩码查表已经是编译期折叠的**（2026-10-24 实测）：`ClassFlagOf` 在
  WASM 画像里是一个独立符号（2.01%），看起来像是渲染器用字面量问"这个节点带不带
  `mbin`"时没有折叠。把它改成 `constexpr` 之后，**配对 A/B 读 -0.15% 与 -0.45%**，
  而同一时间窗的空对照是 -0.28%——**在噪声内**。原因也清楚：残留的那个独立符号是
  `ClassList::Recount` 里的**运行时**名字那条路径，字面量调用点编译器本来就已经
  折叠了。已回退。
- **内核的 1% 改动在这台机器上用墙钟量不出来**（2026-10-24 实测）：不是某一项改动
  没有效果，而是**测量方法本身的分辨率不够**。逐轮配对 A/B 在 JS 胶水上噪声底是
  ±0.3%，在内核上是 ±0.5%–2%（逐轮比值的 p25=92.9%、p75=109.0%），而机器的干扰
  持续的时间远长于一次测量窗口，于是它只打到两个构建中的一个。**结论：内核的改动
  要么用确定量（池分配器的分配计数）来判定，要么把效果做到远超噪声底**——
  不要再用"读数看起来快了 1%"来发布一个内核改动。
- **字体名的查表不是杠杆**（2026-10-24 实测）：`GetCharacterMetrics` 在 WASM 画像里
  是 1.83%（原生只有 0.41%，比值 4.45×），看起来像是每个符号都要做一次名字哈希
  很贵。把字体名的哈希从"逐字节 8 次依赖乘法"换成"一次 8 字节读取 + 一次混合"
  之后，配对 A/B 读 **100.57% 与 100.74%**（= 比基线慢 0.57% / 0.74%），
  而同一时间窗的**空对照是 100.48%**——**在噪声内，而且方向还是反的**。
  结论：这条查表路径不是热点（`GetCharacterMetrics` 的开销主要在度量表本身，
  不在名字上），**不要按画像的百分比去猜热点，要按画像的调用链去猜**。
  已回退。
- **`-mbulk-memory`（`memory.copy` 的固定开销抵消了小拷贝的收益，Node 与浏览器
  实测均无差别）、`ClassList` 的条目偏移缓存（每节点多 24 字节，实测慢 1%）、
  `HtmlOptions` 改用短字符串（24 次/公式的拷贝实测在噪声内，不花钱）、
  线程局部池分配器、去掉 `LexToken` 的 `shared_ptr`（解析时间无变化）。
- **把堆分配全部消掉在原生构建里几乎不涨时间**（glibc 的 malloc 很快），
  收益主要体现在 WASM/浏览器侧；继续压缩分配不是原生 5× 的突破口。
- **markup 拷贝路径不是杠杆**（2026-10-23）：一个公式产生 1262 次 append
  （728 段字符串共 3890 字节 + 535 个单字符），长度分布集中在 1–8 字节。
  把拷贝整个去掉，原生也只快 4.6%——这是天花板。把 `MarkupBuffer::Append`
  的内联逐字节拷贝换成 `memcpy`：原生快 2.0%，**WASM 慢 3.4%**（调用 libc++
  的开销大于拷贝本身）；再叠加 `-mbulk-memory`（让 `memcpy` 变成 `memory.copy`
  指令）：min -0.2%、median +2.9%，落在 null test 的 ±0.9% 噪声里，仍然没有收益。
  结论：**内联逐字节拷贝是对的写法，保持不动**。
- **语义节点的字段布局不是杠杆**：把三个冷字段（`Alignment`、`Text2`、
  `Text3`）挪到 328 B 节点的最后，让渲染器要读的字段落在前几个 cache line 里，
  实测反而**慢 1.4%**。
- **`ArenaText` 不是杠杆**：每公式 153 次调用、拷贝 1325 字节，类名列表的
  二次方重复拷贝并没有显形。
- **语义节点的大小不影响时间**：节点是 328 B，其中四个字段是
  `optional<u16string>`（路线图上想把它们换成字符串池的偏移）。一个只给节点
  **加 120 字节 padding** 的对照实验（只加一个字段，调用点完全不动）显示：
  解析、HTML 阶段、MathML 阶段与整条流水线的差异全部落在交错测量的噪声里。
  语义树的遍历不受节点大小限制。
- **DOM 的形状不是 WebAssembly 多付钱的地方**：在一个关掉 HTML 序列化的
  WebAssembly 构建里，HTML 阶段从 28.1 µs 降到 19.2 µs——**序列化在 WASM 里占
  32%，在原生构建里也占 32%**。WASM 的税在建树（19.2 µs vs 原生 13 µs），
  而建树是 KaTeX 自己的算法。
- **类名一次拼接反而更慢**：类名表是逐个名字追加的，每次追加都把整段文本重新
  拷贝进一块新的 arena，所以 k 个名字会拷贝 k 次。改成"先在栈缓冲里拼好再一次
  写进 arena"，拷贝和块数都减半，实测 **HTML 阶段慢 9.5%**——因为多数类名表
  只有一个名字，本来就只拷贝一次，新写法反而多付了一次长度扫描和一次拷贝。
  结论：**每公式 238 个 arena 块不是 HTML 阶段的瓶颈**。
- **浏览器胶水里的 Latin-1 快路径不值得做**：`TextDecoder.decode` 解 1163 字节要
  0.42 µs，`String.fromCharCode.apply` 只要 1.54 µs。但 36 条语料里只有 **7 条是
  纯 ASCII**（其余含 `∑` 这类多字节字符），快路径只能覆盖五分之一，平均省
  0.4 µs/公式（0.6%）。
- **浏览器胶水里的选项 JSON 不是杠杆**：核心按 JSON 字符串缓存解析结果，基准里
  `displayMode` 来回切换让缓存交替失效，整条路径仍然只有 0.17 µs/公式；
  包自己那一层的 `compileOptions`（不是 `JSON.stringify`）实测 0.46 µs/公式。

### 引导编译：把 profile 交给编译器（2026-10-24，+5–8%）

**做法**：构建 WebAssembly 模块时带上 `native/wasm/katex.pgo`。这个 profile 由
`tools/reference/generate-pgo-profile.mjs` 采集：它把核心编译成一份**带插桩**的
原生程序，跑一遍仓库自己的验收语料（1605 条真实公式，**不是**基准的 36 条），
再用 `llvm-profdata` 合并。

**为什么它有效**：编译器会把 profile 说成热路径的分支挨着摆在一起。渲染器只有
少数极热的路径（解析器的记号循环、构建器的分派），冷路径很多（诊断、罕见命令）；
不知道 distinguished 的编译器会把它们摊在整个代码段里。

**关键的一步：profile 不必来自目标平台**。Emscripten SDK **没有 wasm 目标的
profile 运行时**（`libclang_rt.profile-wasm32` 不在里面，链接会报
`undefined symbol: __llvm_profile_runtime`），所以 profile 是从**原生**构建采集的。
函数的哈希是名字和结构的哈希，两种目标下相同：wasm 构建读原生 profile 时核心的
每个函数都命中，profile 照常生效。wasm 构建里有 7 个文件没有数据（入口点，以及
语料从不调用的那几个文件），编译器会按文件给一次告警。

**另一件关键的事：profile 必须从发布的源码采集**。第一版 profile 是在核心的一份
副本上采的——那份副本把唯一一处「lambda 捕获结构化绑定」改写了，因为手头的编译器
编不了那个捕获。函数的哈希跟着变了，profile 不再命中它，收益小了 1.7 个百分点
（Node +5.9% 而不是 +7.2%）。现在源码在 `native/core/mathml.cpp` 里手工拆开那个
pair（注释里写了原因），profile 与核心的每个函数都对得上。代价是原生侧
0.3–0.5%，在配对 A/B 的噪声里。

**测量**（2026-10-24）：

| 场所                                         | 读数                                                                  |
| -------------------------------------------- | --------------------------------------------------------------------- |
| Node 的 WASM 配对（最静窗口，空对照 +0.40%） | **+7.2%** / **+2.9%**（两序）                                         |
| 浏览器 core 直测（8 对）                     | 最快轮 **+3.3%**、均值 **+5.2%**、中位轮 **+7.9%**（8 对里 7 对占优） |
| 浏览器门禁                                   | 3.61–3.68× → **3.75–3.81×**（最快轮 **3.93×**）                       |
| 输出的字节                                   | **逐字节相同**——profile 改不了程序算出来的东西                        |

### 为什么浏览器端还没到 5 倍

浏览器整条路径是三段相乘再加一段：

```
浏览器路径 = 原生内核 × WASM 的税 × 浏览器相对 Node 的税 + JS 那一层
```

用当前源码（v33）在这台机器上量的因子：

| 因子                               |              读数 | 怎么量的                                                                                                                                                                                                                                                                                |
| ---------------------------------- | ----------------: | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 原生内核（clang 20 + libstdc++）   |       **26.4 µs** | 原生侧配对 A/B 的驱动（进程 CPU 时间，每组取最小值，空对照 100.19%）：这几轮把它从 28.7 µs 降到 26.6 µs，累计配对 A/B 读 +20.5%。阶段分解（消融法）见下                                                                                                                                 |
| WASM 的税                          |   **×1.5 ~ ×1.8** | 浏览器里裸 `vt_render` 是 44–52 µs/公式，对原生 29.3 µs 是 **1.5–1.8 倍**；Node 里整条流水线 58 µs 对原生 29.5 µs 是 **1.97 倍**（含 JS 调用的开销）。**按阶段拆开（WASM ÷ 原生）：解析 1.65×、HTML 树构建 2.19×、HTML 序列化 2.55×、MathML 1.44×**——税集中在把布局变成标记文本的那一段 |
| 浏览器相对 Node                    | **×1.11 ~ ×1.19** | 浏览器里的核心 50.9 µs vs Node 里的 WASM 核心 46.0 µs（中位数）；42.6 vs 35.7（最快轮）                                                                                                                                                                                                 |
| JS 那一层（胶水 + npm 包自己那层） |         **+6 µs** | 逐段拆解：公开 API ÷ 裸 `vt_render` = 1.146，即 JS 层占内核的 14.6%；解码只有 0.42 µs，编码 1.2–1.4 µs，选项 JSON 0.46 µs，其余是 promise 与结果对象（**这一行是换成同步快路径之前测的**：异步包装摘掉之后公开 API 再快 1.9%，这一层约 5 µs）                                           |

于是：26.4 × 1.65 × 1.15 + 6 ≈ **56 µs**（取 WASM 税的中位 1.65），
也就是 Chrome 里 KaTeX 的 **156–189 µs** 的 **2.6–3.2 倍**。基准脚本本身在 `displayMode` 交替的语料上
读 **3.11–3.63 倍**（当前构建三次运行读 3.59× / 3.63× / 3.63×；上一版读
3.44× / 3.44× / 3.42×；换成同步快路径的
JS 胶水之后，五次运行读 3.11× / 3.26× / 3.29× / 3.25× / 3.35×；v33 之前的读数是
3.16× 与 3.17×，v32 是 3.26× / 3.33× / 3.33×，v31 是 3.23×，再往前 v31 是 3.12× /
3.14×，v30 是 3.06× / 3.15× / 3.16×）。
门禁脚本给出的绝对读数是：KaTeX **5.5–5.6 ms**（最快轮）/ 6.2–6.3 ms（中位轮）、
VelociTex **1.5 ms** / 1.7 ms，也就是每公式 KaTeX 153–175 µs、
VelociTex 41.7–47.2 µs。

**5 倍需要原生内核 15.5–19.5 µs**：
KaTeX 最快轮的 ~153 µs 给出 ~30.6 µs 的预算，中位轮的 ~190 µs 给出 ~38 µs；
减去 6 µs 的 JS 那一层，再除以 1.65 × 1.15 = 1.8975。
也就是比现在的 26.4 µs **再快 25–40%**。这比"把三段都重写一遍"所需的时间还多：

| 路线                                                        | 原生内核 | 浏览器路径 |          倍数 |
| ----------------------------------------------------------- | -------: | ---------: | ------------: |
| 现在                                                        |  26.4 µs |     ~44 µs |          3.6× |
| 三段都重写（一趟解析 + 扁平 HTML 渲染器 + MathML 边建边写） | ~18.5 µs |     ~35 µs | **~4.5–5.4×** |
| 再加上重写顺带把 WASM 的税从 +39% 压到 ~+35%                | ~18.5 µs |     ~33 µs |     ~4.7–5.7× |
| 再加上 JS 那一层归零                                        | ~18.5 µs |     ~29 µs |     ~5.4–6.5× |

**结论**：浏览器里的 5 倍不是一个"再优化 30%"的目标，它要求**三段管线重写**，
**再加上**另外两件里的一件（WASM 的税压下来，或 JS 那一层归零）。
这个结论比"再找几个 1% 的优化"要硬得多，因为它给出了每个因子的
具体倍数，也解释了为什么剩下的可做项（profile 里每个函数都不到 10%）
**加在一起也到不了 5 倍**：它们动的是 1% 量级的项，而缺口是 32–45%。

**WASM 的惩罚落在渲染器上，不在解析器上**。把 WASM 构建按同样的口径拆成三段
（`parse = mode1 + mode2 - mode0`，进程 CPU 时间，原生与 WASM 同一时间窗）：

| 阶段                 | 原生 (gcc) | 原生 (clang) | WASM (Node) | WASM 的额外开销 |
| -------------------- | ---------: | -----------: | ----------: | --------------: |
| 解析                 |    6.33 µs |      5.23 µs |     5.68 µs |             +9% |
| HTML 构建 + 序列化   |   18.31 µs |     16.30 µs |    26.31 µs |        **+61%** |
| MathML 构建 + 序列化 |    5.93 µs |      5.86 µs |    10.12 µs |        **+73%** |
| 合计                 |   32.23 µs |     29.33 µs |    42.11 µs |        **+44%** |

解析器在 WASM 里**并不慢**，慢的是两个渲染阶段：14 µs 的额外开销全部落在这里。
这修正了此前"WASM 慢在解析器"的印象，也把下一阶段的重点从解析器移到了渲染器。

这一轮的几次改动都作用在"少调用 libc++"上，MathML 阶段的税因此从 +90% 降到
约 +70%（同一时间窗内实测：WASM 的 MathML 阶段 13.49 → 12.09 µs，原生不变），
但 **HTML 阶段的税基本没有动**（WASM 26 µs，与改前持平）——它是 5 倍目标上
剩下的最大一块。

v27 的两处改动都是冲着 profile 里那 4.8% 的 libc++ 调用去的：

- **字体名的比较**（`native/core/html/options.cpp`）：字体的度量对每个符号都要查一次，
  哈希表命中之后还要用 `memcmp` 确认一遍名字。名字只有十来个字符，
  在 WASM 里这一次 `memcmp` 的**调用**比比较本身还贵；改成内联的 8 字节比较。
- **MathML 的注解**（`native/core/mathml.cpp`）：注解就是公式的源文本，
  原来先编码成一个 `std::string`（一次堆分配），再转义写进输出；
  现在 UTF-8 编码和转义一趟做完，直接写进 markup 缓冲。

v28 的两处改动把热路径上的堆分配和字符串库调用再去掉：

- **空格的类名表**（`native/core/html/build_html.cpp`）：`\ `、`~`、`\\` 这些
  节点的类名表原来是一个 `std::vector<std::string>`（一次堆分配），
  现在直接是 `ClassList`。
- **属性的长度**（`native/core/html/domtree.cpp`）：SVG 属性的长度原来先格式化进一个
  `std::string`，现在格式化进栈上的缓冲（`StackText`）。

原生侧这几处**没有可测差异**（libstdc++ 会把短串操作内联，堆分配也便宜），
收益只在 WASM 侧出现——这正是"看起来什么都没变"的改动必须用 WASM 侧测量才看得见
的原因。

#### v35：省掉的是"运行时的守卫"，不是算法

这一轮的三处改动有一个共同点：**它们没有改算法，只是把一次运行时的调用换掉了**，
所以原生侧几乎读不到，WASM 侧却能读到 4–5%。

- **复用的状态不再走 `thread_local` 的初始化守卫**
  （`native/core/state.hpp`，以及 `html/domtree.cpp`、`pool_alloc.cpp`、
  `mathml.cpp`、`macros.cpp`、`html/options.cpp`、`wasm/katex_wasm.cpp`）：
  一个 `thread_local` 变量的类型只要有构造函数或析构函数，**每一次访问都要先调用
  运行时的初始化守卫**。这些状态在热路径上被访问了几百次：节点 arena 每公式约
  300 次 bump 分配，MathML 写入器的节点表每个节点一次，WASM 入口每个公式四次。
  守卫在 Emscripten 里是 `__tls_init` 这个真实函数调用，在原生构建里是一次
  `__tls_get_addr` 的 PLT 调用加一个分支。
  做法是：把这些状态声明成**命名空间作用域的对象**。WASM 构建里它就是一个普通
  全局，模块启动时初始化，访问它不花任何代价；原生构建里它仍然是
  `thread_local`（.NET 端点会从多个线程渲染），但 arena 与分配池的类型被改成了
  **平凡可构造且平凡可析构**（去掉成员初始化器，零初始化就够），于是连守卫也
  不需要了——`thread_local` 的平凡类型是常量初始化的。
  量：WASM 侧 Node 配对 **+4.45%**（"最静窗口"），浏览器 core 直测最快一轮
  **-5.2%**、中位轮 **-4.0%**；原生侧配对 A/B **+0.86% ~ +1.54%**。
- **类名表不再清零它从不读的那 108 字节**（`native/core/html/domtree.hpp`）：
  `ClassList` 里的名字数组原来有默认初始化器，于是**每一个类名表**都要被清零
  108 字节，而只有前 `count_` 个名字会被读到。一个公式有几百个类名表。
  去掉初始化器之后，拷贝与移动必须只搬运实际持有的名字，所以类名表自己写了
  拷贝与移动（只复制 `count_` 个名字），不再读未初始化的字节。
  悬垂类名检测器（`VELOCITEX_CHECK_CLASS_NAMES`）在整个语料上跑下来零告警，
  HTML 逐字节 5,411/5,411 不变。
- **垂直列表的子项不再整体清零**（`native/core/html/build_common.cpp`）：
  `std::vector::emplace_back()` 会**值初始化**整个子项（184 字节），而子项里
  马上要写的字段随后又被写一遍。给子项写一个用户提供的构造函数，值初始化
  就不再清零整个对象。

**这三条的共同教训**：在 WebAssembly 里，**"是不是一次运行时的调用"比
"做了多少工作"更要紧**。这与"变长 `memcpy` 要换成定长内联拷贝"是同一条规律的
两个侧面（见上文第三批）：libstdc++ 会把短串操作内联掉，libc++ 不会。

#### v36：字体的度量按下标查——确定性的工作量少了，时间没动

KaTeX 按**字体的名字**查一个符号的度量。名字只有二十来个，哈希表命中之后还要
比较一遍名字。VelociTex 原来照搬了这个做法：**每个符号查一次**。

改成一个 `FontId` 枚举（KaTeX 的度量表里那二十个字体）之后，名字只在模块启动
时解析一次，符号的度量查表变成一次数组下标。**确定性的计数**：那 36 条语料上，
字体的度量一共查了 782 次（每公式 21.7 次），而**字体的名字被哈希了 0 次**
（启动时的 20 次除外）。

顺带修掉的两处堆分配：大分隔符的字体名原来是用 `std::to_string` 拼出来的
（`"Size" + std::to_string(size) + "-Regular"`，每个分隔符一次堆分配），
现在是一张表的下标。

**但是时间没有动**：原生侧配对 A/B 读 +0.35% / +0.58%（空对照 ±0.6%），
Node 的 WASM 配对读 +0.59% / +0.75%（空对照 ±0.7%），浏览器 core 直测的最快
一轮与中位轮互相抵消。**这一项是"工作量确定地少了、时间读不出来"**——它被
发布不是因为它快，而是因为它去掉了一个热路径上的哈希表，并且让字体成为一个值
而不是一段字符串。

**这一项还修正了一个测量上的误解**：WASM 画像里 `GetCharacterMetrics` 占 1.9%，
看上去整个哈希都在里面；实际上哈希只占其中的一小部分，剩下的是度量表本身的查找。
**画像里的百分比不等于"可以拿掉的那部分"**。

**测量的注意事项**：这台机器的噪声随负载变化，同一协议的空对照在
-0.01% ~ +0.74% 之间摆动，所以单次读数不能当结论。上面每一行都至少测了三次，
报告的是中位数。

### 编译器差异：原生数字是 GCC 数字，它藏起了一半的 WASM 税

同一份源码、同一套标准库（libstdc++）、同一台机器、同一份语料，只换编译器：

| 阶段                 | gcc 11.4 + libstdc++ | clang 20 + libstdc++ |       差 |
| -------------------- | -------------------: | -------------------: | -------: |
| 解析                 |              6.32 µs |              5.24 µs | **-17%** |
| HTML 构建 + 序列化   |             19.28 µs |             16.08 µs | **-17%** |
| MathML 构建 + 序列化 |              6.79 µs |              6.69 µs |      -1% |
| 合计                 |         **33.92 µs** |         **29.71 µs** | **-12%** |

WASM 构建用的就是 clang，所以上面"原生 34 µs vs WASM 43.8 µs = +29%"其实是
**拿 clang 构建去比 GCC 构建**。同一时间窗内按同口径重测：

|                      | 原生 (clang) | WASM (clang + libc++) | WASM 的额外开销 |
| -------------------- | -----------: | --------------------: | --------------: |
| 解析                 |      5.24 µs |               5.01 µs |            持平 |
| HTML 构建 + 序列化   |     16.08 µs |              27.44 µs |        **+71%** |
| MathML 构建 + 序列化 |      6.69 µs |              12.70 µs |        **+90%** |
| 合计                 | **29.71 µs** |          **45.14 µs** |        **+52%** |

结论有两条：一是**税在引擎与 libc++，而且全在渲染器**（解析器在 WASM 里并不慢，
甚至比原生快）；二是**MathML 渲染器是 WASM 下最敏感的一段**（+90%），它按节点
建图、记属性表、再序列化，是下一步最该动的地方。

> **这张表之后又变了一格**：v25 把 MathML 的值池换成 markup 缓冲、符号文本直接进池
> （见下面的增量表），MathML 阶段的税因此从 +90% 降到约 +70%（WASM 侧 13.49 →
> 12.09 µs，原生侧不变）。**HTML 阶段的税基本没有动**（WASM 26 µs，与改前持平），
> 它是浏览器 5× 目标上剩下的最大一块。同一时间窗内重新测的三个因子是
> **+44%**（合计）、HTML **+61%**、MathML **+73%**（见"为什么浏览器端还没到 5 倍"）。

### 当前源码的 WASM 侧 profile，以及"调用者"是怎么读的（2026-10-24）

先说两个让 profile 说谎的坑，这一轮都踩过：

- **DWARF 展开失败会造出假热点。** `perf record --call-graph=dwarf` 把
  132,234 个样本里的 132,055 个落在同一条 `callq HtmlNode::WriteMarkup`
  指令上，行级画像因此报出"`domtree.cpp:392` 占 19.57%"——而符号级画像里
  `WriteMarkup` 连前 12 名都没进。**行级画像只有和符号级画像对得上才算数。**
- **扁平画像是诚实的。** `perf record -F 4000` **不加** `-g` 只记指令指针，
  `perf report --no-children` 给出的就是每个符号的自耗时，没有展开，就没有
  错误归属。PIE 的地址要减去加载基址（`perf script --show-mmap` 里该二进制
  的第一个 `r--p` 映射）才能给 `llvm-addr2line` 解析，而且要用 Emscripten
  工具链里的 `llvm-addr2line`（系统自带的读不了 clang 20 的 DWARF 5）。

WASM 侧也能画像：Node 的 V8 profiler 按**函数索引**给帧命名，而发布模块的
name section 被剥掉了，所以要另外构建一个 `-g2` 的**孪生模块**做画像——它的
code section 与发布模块**逐字节相同**（804,487 字节，同样的字节），函数索引
也就相同，名字可以直接用。**调用者**要从 profile 的调用树里读，这是分辨
`memcmp` / `memcpy` / `strlen` 来自哪里的唯一办法。

当前源码在 WASM 构建里的分布（36 条冻结公式）：

**模块里确实有对 C 库的调用，调用点是数得出来的。** 发布模块的 name section
被剥掉了，所以要在**孪生模块**上数（它的 code section 与发布模块逐字节相同）：
batch 10 的模块里有 **301 个 `__memcpy`、302 个 `memcmp`、104 个 `memmove`、
482 个 `__memset`、47 个 `strlen` 调用点**。**用剥掉名字的模块去 grep 会读出
零**——名字没了，grep 什么也找不到；要在孪生模块上搜。画像给出的时间是
`__memcpy` 2.3%、`memcmp` 0.3%、`strlen` 0.5%、`__memset` 0.3%、`memmove` 0.2%，
合起来是流水线的约 3.5%，而每一个调用点都是一次省指令的机会。

原生侧的形状相同：解析 19%、HTML 建树 22%、HTML 序列化 16%、MathML 11%，
样式声明里的 `em` 值再占 5.7%。**没有任何一项超过 14%**——这就是为什么那些
百分点的改动加不到 5 倍的缺口上（见"为什么浏览器端还没到 5 倍"一节）。

**这一轮真正抓到的调用点。** profile 里的 `memcmp` 不是引擎的事，是渲染器
在拿 `string_view` 和字面量比较：`basic_string_view::compare` 比较的是两个
长度中**较短**的那个，这个长度只有运行期才知道，于是 `memcmp` 无法被内联，
**每一次比较都是一次对 C 库的调用**。而渲染器对每个原子都要问好几次：
`SpacingBetween`、`cancel_bin`、`IsMathClass` 都在比较节点的类，MathML 的写入
器在比较节点的标签。调用者的读数是：

| 调用者                                    | `memcmp` 的时间 |
| ----------------------------------------- | --------------: |
| `Writer::write_attributes`                |         15.7 ms |
| `Writer::build`                           |          9.9 ms |
| `Builder::BuildExpression`（两个 lambda） |    8.5 + 7.4 ms |
| `RetrieveTextFontId`                      |          3.7 ms |

现在字面量按**编译期已知长度**来比（`same_text(a, "mord")`），是一次加载加一次
比较，没有调用。

- **发布的那一处**：Node 配对 A/B 读 **+1.31% / +1.48%**（两序同向），
  浏览器 core 直测中位轮 **9.800 ms → 9.450 ms（-3.6%）**、最快轮
  8.700 ms → 8.650 ms，原生配对 A/B 读 +1.37% / -0.93%（空对照 +0.10%）。
  原生侧中性是应该的——省掉的那次调用在原生构建里本来就很便宜。
- **负结果**：同样的改动用在 UTF-16 那一侧（解析器的命令名、符号表与宏表的
  哈希）是**倒退**：Node 配对 A/B 读 -0.72% / -1.71%（两序都更慢）。对五到十五
  个字符的名字，逐字符的循环比一次调用慢，而内联的字面量又让模块变大。
  只有渲染器那侧比较短字面量的部分被发布。
- **profile 的坑**：发布的那处改动，**第一版构建慢了 1.5% 与 4.5%**，原因就是
  profile——核心的 profile 是构建输入，被改动的函数已经对不上它了。
  **测量一项核心改动，先要一份从改动后的源码采来的 profile**
  （`node tools/reference/generate-pgo-profile.mjs`）。换成新采的 profile，
  同一份源码读 +1.31% / +1.48%。

**这一轮的判定性实验**：把 HTML 的序列化整段关掉（`HtmlNode::WriteMarkup` 直接返回），
只留建树，测得 parse+html 从 24.58 µs 降到 18.80 µs。于是：

| 原生 32.2 µs 的构成  |     µs |    占比 |
| -------------------- | -----: | ------: |
| 解析                 |    6.3 |     19% |
| **HTML 树构建**      | **13** | **39%** |
| **HTML 序列化**      |  **6** | **18%** |
| MathML 构建 + 序列化 |    6.5 |     19% |

**这否定了"直接输出 markup、不建 DOM 树"这条主路径的收益预期**：省掉序列化最多只省
18%，建树那 38% 是 KaTeX 算法本身的工作（算尺寸、排 vlist、定类名与样式），
省不掉。AGENTS.md 里"HTML 直接输出 markup"作为主要杠杆的估计需要按这个数据修正。

热点分布确实已经很平（`perf`，17,698 个采样点，原生 parse+html+mathml 34.0 µs/公式）：

| `AppendEm`（`makeEm`）                 | 2.70% |  3.50% |     1.30 |
| `Expand`（宏展开）                     | 2.79% |  3.42% |     1.23 |
| `memcpy` + `memmove`                   | 2.13% |  3.18% |     1.49 |
| `ClassFlagOf`（类名比较）              | 1.73% |  2.14% |     1.24 |
| `GetCharacterMetrics`（字体度量）      | 0.41% |  1.83% | **4.45** |
| `MakeOrd`                              | 0.65% |  1.39% |     2.14 |
| `BuildArrayNode`                       | 0.86% |  1.33% |     1.55 |
| `MarkupBuffer::Append`                 | 5.05% |  2.43% |     0.48 |
| `ArenaText::Assign`                    | 2.35% |  1.66% |     0.70 |
| `Builder::BuildGroup` 等（HTML 建树）  | 7.40% |  5.68% |     0.77 |

**这张表有一个陷阱，必须先说清楚：逐函数的比值会被内联差异污染。**
原生构建把 `HtmlSpan::WriteBody` 单独留成了符号（1.30% + 3.78% = 5.08% 的
HTML 序列化），而 WASM 构建把它内联进了 `HtmlNode::WriteMarkup`（5.70%）——
所以"2.37×"是记账方式造成的，不是真的慢了两倍多。把内联的部分合起来看：

| 部分                                   |   原生 |   WASM |     比值 |
| -------------------------------------- | -----: | -----: | -------: |
| HTML 序列化（WriteMarkup + WriteBody） |  5.08% |  5.70% |     1.12 |
| HTML 建树（Builder::Build* 合起来）    |  7.40% |  5.02% |     0.68 |
| MathML 写入器（walk + 建图 + 序列化）  | 10.86% | 14.89% | **1.37** |

**按阶段的税率才是真的**：解析器 **+16%**、HTML 阶段 **+27%**、MathML 阶段 **+37%**。
三条结论：

1. **解析器几乎没有 WASM 税**（1.16×，+1.5 个百分点）。税全在渲染器里。
2. **HTML 那一侧的税是摊开的**：建树在 WASM 里**反而更便宜**（0.68×，也是内联
   造成的记账差异），序列化基本持平（1.12×）。也就是说，HTML 阶段那 +27% 并不
   集中在某一个函数上，而是"每个函数都慢一点"——这与"WebAssembly 慢在内存访问
   上"一致：越是逐节点走树、每写几个字节就要做一次边界检查的代码，差得越多。
3. **真正集中的那一块是 MathML 写入器**：`write_mathml`（走语义树、算样式与
   尺寸）+ `Writer::build`（建节点图）两个函数就贡献了 **+4 个百分点**的税，
   占整个 MathML 阶段的一半。
4. **按流水线占比，HTML 渲染器（~34%）仍然是 MathML 写入器（~16%）的两倍**，
   所以路线图里"HTML 直接输出 markup"仍然排在"MathML 边建边写"**前面**——
   与上一版路线图的顺序相反。

可行的加速路径（按收益排序）。**其中两项已被实测排除**（语义节点的大小、DOM 的
形状），路线图因此变短了。**2026-10-24 的逐函数对照把第 1 项和第 4 项换了位置**：
HTML 渲染器占流水线的 ~34%，MathML 写入器只占 ~16%，所以 HTML 那一项排在前面。

1. **HTML 直接输出 markup**（最大的一块：HTML 渲染器占流水线 ~34%）：需要把
   `build_html.*` 的返回类型从 `HtmlNodePtr` 改为"边算边写"或引入轻量 span 视图。
   **上限只是上限**：序列化那部分（`WriteMarkup` 6.55% + `AppendEscaped` +
   `MarkupBuffer::Append` + `CssStyle::WriteTo`）大约是流水线的一成，
   而**建树那部分省不掉**——尺寸、vlist、类名与样式都是 KaTeX 算法本身的工作，
   而且树的形状已经证明不是 WebAssembly 多付钱的地方（建树在 WASM 里反而便宜
   0.77×）。**难点在顺序**：KaTeX 先建子节点再算父节点的样式，而 markup 的顺序是
   父在前、子在后，所以父节点的开标签必须在子节点建好之前写出来——这要改
   `build_html.cpp`（1,980 行）、`build_common.cpp`（806 行）以及 accent /
   array / delimiter / enclose 四个模块，是**重写级**改动。
2. **MathML 渲染器改成"边建边写"**（WASM 下最敏感的一段，+73%）：`Writer::build`
   先按节点建图、记属性表与值池，`Writer::serialize` 再遍历一遍；直接输出可以
   去掉整张图与第二次遍历。
   **这一项的形状和上界都已经量过**（消融法，见"这张表是怎么量出来的"一节）：
   建图 ~5.2 µs + 序列化 ~3.0 µs = **~8.2 µs = 整条 WASM 流水线的 17%**，
   而遍历只有 1.4 µs。**旧文档估的"这阶段的 60%"偏乐观**——WASM 口径下建图与
   序列化加起来是这个阶段的 ~50%，折合整条流水线 17%。
   **一个已经排除的子项**：属性值里的数字（`number()` / `em()`）每公式只调用
   **0.86 次**——不是热点，改写它没有意义（`std::to_chars` 的科学计数法加一堆
   `std::string` 操作看着吓人，但公式里几乎没有数字属性）。
   **另一个已经排除的子项**：值池不是建图成本的主因（禁用 `pool.intern` 的探针
   构建只快 0.64%），所以"边建边写"的净收益只有 **-10%**（序列化的工作只是搬家）。
   **难点不在"写"，在"顺序"**：KaTeX 先建子节点再算父节点的样式，而 markup 的
   顺序是父在前、子在后。合并不了的兄弟节点要等下一个兄弟才知道（`Writer::merge`），
   而 `<mrow>` 外壳要等整行数完才知道要不要写——所以"边建边写"要么给外壳预留
   位置再回填，要么给每一行一个暂存缓冲。
   **还有一个结构性障碍**：`Writer::build` 里父节点会**回头修改子节点**（给分子、
   分母补 `LSpace`/`RSpace`，把兄弟节点串成链表），所以一次前向遍历写不出结果。
3. **渲染器里的 `std::string` 换成 `string_view` + 单块输出缓冲**：这正是 WASM
   侧多出来的 13 µs 的所在（HTML +61%、MathML +73%，按同编译器口径）。原生上
   收益小（glibc 的 `malloc` 便宜），WASM 上收益大。
4. **解析器重写**（当前 18%）：去掉 `LexToken` 的 `shared_ptr` 引用计数、
   `Tasks` 向量的搬移与 328 B 的语义节点临时量，宏展开改为直接递归下降。
   **注意两点**：语义节点的**大小**已经证明无关（见上），而**解析器在 WASM 里
   并不慢**（5.7 µs，只比原生慢 9%；逐函数对照里 `ParserState::Run` 只有 1.16×），
   所以这一项对浏览器端的 5× 目标帮助最小，只能缩短原生侧。

即便 1–4 全部完成，乐观估计也只有 3–4 倍；**5 倍需要更激进的路线**（例如一次性
编译的解析器 + 直接输出 KaTeX 盒模型的扁平渲染器），属于重写级工作量。

## 浏览器门禁的分辨率：它分辨不出 3% 的改动

基准的一轮渲染 36 条公式，核心这一轮约 1.7–2.1 ms，而 Chromium 的
`performance.now()` 分辨率是 100 µs —— **每公式的量化步长是 2.8–3.5 µs**
（相对核心是 6–7%，相对 KaTeX 是 0.3%）。同一个构建跑三次读到 3.26× / 3.33× / 3.33×，
3% 的改动**不会让这个数字动**（v33 只动了错误路径，读数是 3.16×，机器负载更重）。

要在门禁里看出这种量级的改动，只有两条路：

- **在计时轮内重复语料**：一轮里把 36 条公式渲染 6 次（轮长 ~11 ms），量化步长
  降到 0.46 µs/公式。这是本项目现在测浏览器逐段差异的办法。
- **同一页面里两个变体的配对 A/B**：两个变体共用同一个
  WebAssembly 实例（它们 import 同一个模块），每一轮按 A,B,B,A 的顺序背靠背测量，
  报告逐轮比值的中位数。本轮用它测出：去掉包的内层 promise 是 **0.00%**，
  把 `async function` 换成返回 promise 的普通函数也是 **0.00%** —— 这两处
  因此**没有发布**（改动本身无害，但既然量不出收益，就不留在代码里）。
