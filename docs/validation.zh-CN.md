# 兼容、视觉、性能与内存验收

[English](validation.md) | 中文

**2026-10-19 验收更新：** 用户明确表示“可以放宽抗锯齿不一致的要求，只需要排版正确即可”。下文栅格边缘/RGB 阈值保留为历史诊断，不再阻断验收。语义、字形/字体与顺序、数学结构几何、基线/间距、颜色和裁剪仍严格检查。`verify-p4.ps1` 通过 `--layout-only` 保留原始像素指标；数学差异和裁剪仍使验证失败。

本文件给出可执行的验证协议。10ms 是用户确认的首版门槛；其余数值都是待 P0 校准后冻结的工程初始预算，需记录理由，不是本轮已测得的结果。

## 1. 对照基线与产物

使用 [锁定清单](reference/katex-0.19.0.lock.json) 指定的 KaTeX 代码、发行包和字体，并把浏览器、开发 runtime、OS 与工具版本写入运行 manifest。测试工具只在开发与 CI 中使用浏览器，正式运行时不使用。

每个 fixture 的输出目录至少包含：

```text
run-manifest.json
compatibility.json
fixture-id/
  input.json
  reference.mathml
  reference.geometry.json
  reference.png
  native.layout.json
  native.png
  output.svg
  output.mathml
  diff.png
  metrics.json
summary.json
```

JSON 记录输入、选项、宏状态、字体与数据摘要、逻辑尺寸、基线、关键节点位置、ink bounds、结果和失败原因。截图、包和源码版本相互关联，不能用旧截图证明新源码已经通过。

## 2. 兼容清单与语料

清单从固定版本的注册表、符号、宏和传递依赖中提取，既记录独立实现，也记录别名。每项标注状态：已纳入或有理由排除，以及语义、几何、MathML、原生、PNG、SVG 各项的结果。发布报告保留原始分母。

语料来源：

- 本仓库的 [公式种子集](examples/formulas.json)。
- 上游 [katex-spec](https://github.com/KaTeX/KaTeX/blob/v0.19.0/test/katex-spec.ts)、[mathml-spec](https://github.com/KaTeX/KaTeX/blob/v0.19.0/test/mathml-spec.ts) 与 [screenshotter-spec](https://github.com/KaTeX/KaTeX/blob/v0.19.0/test/screenshotter-spec.ts) 中属于范围内的用例。
- 按命令、符号、环境和主要选项生成的覆盖；关注语义分支与交互组合，而不只测 happy path。
- 组合用例：微积分、矩阵与数组、嵌套上下标、伸缩符号、特殊盒、宏作用域、中英文文本。
- 负例：无效输入、超限、循环宏、取消、并发隔离，以及资源生命周期的反复创建与释放。

种子集只用于启动工具，不能作为完整兼容证明。上游的浏览器与扩展用例被显式排除，也不能把未实现的数学命令误归为扩展。

## 3. 语义与 MathML 硬门槛

- 同一输入与选项下，成功 / 失败分类符合范围定义与公开的资源上限。
- 核心节点类型、分组、字形与字体选择、参数、环境行列数和宏展开结果正确。
- 缺字、丢失节点、错序、上下标附着错误、分母线或根号线漏画、矩阵缺行缺列，一律判为失败，与截图相似度分数无关。
- 常规错误具有稳定的错误码和源位置；失败或取消不会破坏引擎、workspace 或宏会话。
- MathML 按 XML namespace 和规范化后的树比较，忽略属性顺序和无意义的序列化差异，但保留文本、结构、运算符与 display 语义。
- 不能统一折叠所有空白：`mtext` 中的空白有语义，允许的差异必须指明节点与规则。
- 复制应得到完整原文；默认隔离宏、显式会话和缓存命中都按契约验证。

正式的核心兼容要求所有范围内注册项都被覆盖，并且以上硬门槛 100% 通过。

## 4. 几何与视觉验收

### 4.1 参考端正确测量

使用真实浏览器布局，不用 jsdom 尺寸或 `renderToString` 的估计代替。加载精确的 CSS 与字体，等待 `document.fonts.ready`，并逐项确认用到的字体已加载。固定视口、DPI、zoom、主题与字体回退环境，关闭动画。

公式自身 em 与原生 `FontSizeDip` 相同；需处理 KaTeX 外层 1.21 倍字号，避免二次缩放。MathML 的无障碍节点不参与视觉 bounding box。用基线探针测量实际 baseline，对照公式逻辑盒与墨迹盒；带标签的测试显式设置相同的容器宽度。

参考节点几何来自实测的 DOM 与 glyph 范围。必要时可在固定版本的测试构建中增加节点映射，但不得改变样式或布局。生成的规则数据可用于解释结果，但不能用自己的规则验证自己。

### 4.2 初始容差

以下按公式有效 em 与 DIP 计算，并在 P0 用单字形、已知正确的手工构造和参考端噪声校准后冻结：

| 比较项 | 工程起始容差 |
| --- | --- |
| 基线、数学轴、主要子节点位置 | `max(0.02em, 0.35 DIP)` |
| 分数线、根号线、上下标最小间隙等 | `max(0.015em, 0.25 DIP)`，同时满足不相交等数学关系 |
| 总 advance / height / depth | `max(0.04em, 0.75 DIP)`；长数组另检查逐列偏差，不能只放大总宽容差 |
| 裁切、缺字、缺路径、矩阵行列错误 | 不允许 |
| 光栅边缘 | 至少 95% 前景边缘点的双向距离落在 `max(1 device pixel, 0.5 DIP 对应像素)` 内，并按类别报告 |

先按基线与声明坐标对齐，不允许为提高分数逐公式平移、缩放或形变。唯一允许的全局截图变换，是把记录好的同一公式原点映射到共同画布。

边缘指标、SSIM 和像素差都作为诊断证据，不用大面积背景稀释错误。像素相同率或“95% fixture 通过率”都不能直接解释为“95% KaTeX 兼容”。超过自动容差的用例必须复核原因、修复，或记录经审查的抗锯齿 / 系统回退差异；未解决的数学排版错误一律不能留下。

P0 可以统一调整起始阈值，但必须保留调整证据；之后不能针对失败个例无说明地放宽。通过率按类别独立统计，少见类别不能被大量简单公式掩盖。

### 4.3 场景矩阵

- 行内与独立样式，显式覆盖各数学 style 及 cramped 分支。
- 至少 16 / 24 / 32 DIP 字号，以及 100 / 125 / 150 / 200% DPI。
- 深浅主题、显式颜色，以及放在深浅背景上的透明 PNG。
- 空输入、普通、复杂、超长、错误和资源超限输入。
- 大小矩阵、负间距、重叠、phantom、伸缩路径与大分式。
- 同尺寸 PNG 与 SVG 在受控查看器中的渲染，SVG 可在未安装字体时打开。
- 真实 WinUI 控件、相邻正文与标点、宽窄窗口、滚动，以及卸载 / 重载。

每次 UI 改动后运行真实应用、自动截图并人工查看受影响画面；示意图、离屏引擎单元图或 Computer Use 都不能替代真实宿主截图。PR 可以运行冻结的分层小集合，正式候选运行完整矩阵；与本次改动无关且已通过的昂贵检查不无理由重复。

## 5. 10ms 的精确定义

计时区域：完整公式已在内存 → 选项与资源校验 → 词法 → 宏展开 → 语义 → 布局 → 完整绘制指令与不可变结果生成。包含必需的文本 shaping 与结果分配，不允许把这些工作延后到“计时之外的渲染准备”。

前提：字体、规则数据与图形设备初始化完成；JIT 测试已预热或直接使用 AOT；公式、语义与布局结果缓存关闭。允许长期驻留的固定字体资源和静态表；字体与 glyph 查表策略写入 manifest。glyph / text shaping 缓存的冷 / 热差异单独报告。

门槛：在冻结的代表性普通语料上，整体与各主要类别均为 **P95 ≤10ms**。同时报告 P50、P95、P99、最大值与分配量；超大压力输入单独报告，不混入普通语料，也不删除耗时异常点。

普通语料建议覆盖短公式、标准分数与根式、积分与求和、aligned、3×3 / 5×5 矩阵、适度嵌套和短文本。P0 冻结具体集合与输入分布，避免后期只挑简单公式。

测量使用独立的 Release AOT benchmark host 和单调高精度时钟：至少五次独立运行，每个主要类别至少 1,000 个完整调用样本。在同一持久进程内打散公式顺序，避免重复同一公式伪装成无缓存；原始样本全部保留。

测量前可以清理上一轮状态并预热；计时期间不得逐调用强制 GC，也不得隐藏 GC 暂停。核心同步计时与宿主后台排队延迟分开；调度、native prepare、绘制提交、present 与编码各自单独计时。

没有旧 CPU 实测数据时，10ms 验收只对已测机器成立。建议的参考机为约 2015–2017 年的常见双核 / 四线程低功耗 x64 集显；记录型号与功耗策略，不用 VM 的“限制核心数”冒充同等旧 CPU。

## 6. 其他延迟与内存预算

以下是待 P0 校准的工程初始目标，不是用户新增的硬门槛：

| 项目 | 起始预算 / 报告方法 |
| --- | --- |
| 库首次初始化 | 规则、字体与设备分别报告，先以 ≤150ms 为探索预算；不含整套 WinUI 进程启动 |
| 一题 10 条公式 | 无公式缓存、完整宿主接入，先以 P95 ≤50ms 为目标 |
| 一页 100 条公式 | 先把首批可见结果与全部结果分开报告，全部 CPU 就绪后以 P95 ≤250ms 为目标 |
| UI 线程 | 单次提交尽量 ≤4ms，长批次分片；实际帧率与 present 时间单列 |
| 导出 | 按尺寸、字形数分别报告；建议普通式 PNG ≤20ms、SVG ≤10ms、MathML ≤5ms，P0 后冻结 |
| 结果与资源缓存 | 默认每个 engine 16MiB；明确包含哪些 native 资源，GPU 表面另列 |
| 工作缓冲 | 默认最多保留两个 workspace；大于约 1MiB 的单个临时容量不常驻 |
| 常见 100 式增量内存 | 字体初始化后，已有宿主上的私有内存增量先以 ≤32MiB 为目标，并同时报告托管堆与 native / GPU 占用 |

P0 若发现某项探索预算不合理，记录调整原因、负载与替代值；不能靠削减功能或把必需阶段移出计时来“达标”。

内存测试包括：清空内容、1 / 10 / 100 / 1000 条公式；反复打开与关闭页面；大公式后回到小公式；取消与错误；切换主题与 DPI；多线程创建与释放。报告总分配、存活内存、私有字节、提交量、native 对象 / handle 与 GPU 资源。`GC.GetAllocatedBytesForCurrentThread` 只适用于同步托管路径，不能代表整个进程或 native 零分配。

缓存同时受字节预算和条目数约束，不能只限制公式数量。固定字体数据、输入源文、结果数组、outline、位图 / 表面和临时编码缓冲都计入台账，既避免重复引用被重复计费，也避免完全漏算。

## 7. KaTeX 性能比较与 ≥10× 规则

建立三组互相独立的结果：

1. **可对应的核心子阶段。** 用固定版本的测试插桩比较相同工作量下的词法、宏与解析。KaTeX 的虚拟 HTML 构造与本库的布局 / 绘制指令并不完全等价，边界需要分别标明。
2. **预热后的完整视觉工作。** 同一台机器、同一批公式、有效字号、DPI、字体和缓存状态；浏览器从调用 KaTeX 到 DOM 布局与绘制完成，原生从调用到对应的布局与绘制完成。CPU 时间、wall time、提交与实际呈现证据分别测量。
3. **真实的下游体验。** 与原 Typst 链路比较切题、首屏、整页、主题 / DPI 变化和内存。这是迁移收益，不能称作相对 KaTeX 的算法倍数。

`renderToString` 只产生标记，浏览器尚未完成布局与绘制；不能把它与原生完整呈现混作等价流水线，也不能仅凭它快或慢就证明端到端倍数。参考端自身的能力边界见 [KaTeX API](https://katex.org/docs/api)。

只有在两端都排除浏览器 / 应用启动之后，才能讨论预热后的算法或渲染加速。不能用 C# 缓存命中对比 JS 无缓存，也不能用原生只画字形对比浏览器解析加布局。几何正确性与完整输出必须同时达标。

浏览器计算时间不能包含两次 `requestAnimationFrame` 之间那类显示器同步等待；通过浏览器 trace、Windows ETW / present 事件或经过验证的测量工具区分 CPU、GPU 与帧等待。截图捕获在计时区外用于证明结果正确，不能把截图编码计入任何一端。

可声明的 ≥10× 必须写清具体指标和负载，给出固定的语料分布、每类比例、置信 / 稳定性证据以及内存代价。局部阶段达到 ≥10× 时只能对该阶段声明；若端到端仍受帧周期限制，则继续分开报告，不推广成整体倍数。

## 8. AOT、稳定性与包消费

- 在 JIT 和真实 Native AOT 消费程序中运行显示、PNG、SVG、MathML、字体加载与 COM 回调，不以 `IsAotCompatible` 或编译成功代替实际运行。
- 修复而不是隐藏 IL / 裁剪警告，并记录所有遗留问题；验证包的依赖、资源、许可证、TFM 与最低系统版本。
- 随机与生成输入用于验证不崩溃、资源有界、取消可终止；针对 native 代码和 unsafe 边界覆盖尺寸溢出、释放、多线程与设备失效。
- 回归不变量：等比缩放后布局一致；主题变化不改变几何；行内与独立显示的差异符合规则；无状态并发结果一致；失败之后下一条正常公式仍可渲染。
- 在干净工程中从本地 feed 消费 nupkg，确认不是仅靠项目引用、开发目录字体或已安装工具才成功。

每次交付按“通过 / 失败 / 未执行”三种状态报告。未执行项不得用预测数值或其他机器的结果填充。
